# AgentVM CLI tools
![AgentVM Icon](Icon/robot-small.png)

Run AI agents and their tools inside disposable virtual machines on your Mac, running macOS or Linux, so a mistaken, prompt-injected or malicious agent cannot reach the rest of your Mac.

## What it does

An AI coding agent (Claude Code, Codex, opencode, or any tool an agent drives) runs inside a virtual machine - a "box" - instead of directly on your Mac. A box runs macOS, or Linux (Debian) when the work does not need a Mac: a Linux box starts in about 3 seconds and its image takes 2 GB instead of 30 ([Docs/linux-boxes.md](Docs/linux-boxes.md)).

- **Only your project is shared.** The project folder is mounted at the same path inside the box. Your home folder, Keychain, SSH keys, other projects and browser data do not exist there.
- **Network is allowlisted.** The box has no route to your Mac or your local network. Outbound connections go through a proxy on the host that allows only the hosts you choose (package registries, the agent's API) and logs every connection.
- **Every session can be undone.** Before a session starts, `agent-vm` takes an instant snapshot of the project. Afterwards it reports what changed, flags files that run code later on your Mac (git hooks, build scripts, package install scripts), and can restore the snapshot.
- **Boxes are disposable.** A box is a copy-on-write clone of a sealed "golden" image, created in seconds and discarded after use, so nothing an agent plants survives.
- **Model inference stays on your Mac.** Local models keep the full GPU; only the agent and its tools run in the box.

It builds on Apple's Virtualization framework and the zero-click macOS guest setup added in macOS 27.

What a box protects against, what it does not, and what each claim rests on: [Docs/threat-model.md](Docs/threat-model.md).

## Requirements

- A Mac with Apple silicon
- macOS 27 or later (host and guest)
- Disk space for one golden image (tens of GB for macOS, about 2 GB for Linux) plus per-box changes
- For Linux boxes nothing more: the package carries the guest daemon for them, and Debian's cloud image is downloaded when the first image is built

## Installing

Open the installer package, `agent-vm_<version>.pkg`. It installs for you alone, with no administrator password: the tool goes into `~/.local/share/agent-vm/versions/<version>`, and `~/.local/bin/agent-vm` and `~/.local/bin/avm` point at it. It also adds `~/.local/bin` to your shell's `PATH` unless it is there already. Then, in a new Terminal window, `agent-vm doctor` says whether this Mac can run boxes. Details are in [Packaging/README.md](Packaging/README.md); building from source is under [Building](#building).

## Usage

```sh
agent-vm image fetch-ipsw                                # the latest macOS restore image (about 27 GB)
agent-vm image create macos-dev --ipsw latest            # install macOS and set it up - no clicks
agent-vm image create deb --linux debian-13              # or a Linux image: Debian 13, about a minute
agent-vm box create dev --image macos-dev --allow pack:npm --allow pack:github --allow pack:anthropic
agent-vm box start dev
agent-vm session start --project ~/src/myapp             # snapshot, prints the session id
agent-vm exec --box dev --project ~/src/myapp -- claude
agent-vm session report <id>                             # what changed, with risky files flagged
agent-vm session undo <id>                               # restore the project snapshot
```

`agent-vm exec` streams stdin, stdout and stderr, forwards signals and returns the command's exit status, so it can wrap any stdio program - including Agent Client Protocol (ACP) agents and Model Context Protocol (MCP) servers launched by another application.

How images and boxes relate (a box is a copy of its image made once, and never updated from it afterwards), and the everyday procedures - adding tools, upgrading agent-vm, refreshing a box, freeing space - with answers to common questions: [Docs/images-and-boxes.md](Docs/images-and-boxes.md).

How many CPUs and how much memory to give a box, by what it will do and by your Mac's size: [Docs/processors-and-memory.md](Docs/processors-and-memory.md).

## Sessions: snapshot, report and undo

A session protects a project folder while an agent works on it - in a box, or directly on your Mac. It is useful on its own: run it around any agent session.

```sh
agent-vm session start --project ~/src/myapp   # instant snapshot, prints the session id
# ... let the agent work ...
agent-vm session report <id>                   # what changed, with risky files flagged
agent-vm session end <id>                      # optional: mark the run finished
agent-vm session undo <id>                     # put the project back as it was at start
agent-vm session undo <id> --path .mcp.json    # or only some entries (repeatable)
agent-vm session discard <id>                  # delete the snapshot when you no longer need undo
agent-vm session discard --older-than 30       # every ended or undone session that ended 30+ days ago
agent-vm session list                          # all sessions and their states
```

- **The snapshot is instant and nearly free.** Every file is cloned copy-on-write on APFS, so it takes space only as the agent changes files.
- **The report shows what changed and what to look at first.** Additions, deletions, modifications, type and permission changes, with whole new or deleted folders collapsed to one line. A change is found by content, not by modification time: a file is unchanged when its status-change time (ctime, which a process cannot set), and that of every folder above it, is older than the session start (a moved folder gets a new ctime, the files inside it keep theirs); every other file is compared with its snapshot copy, instantly while both are still APFS clones of the same data, otherwise byte for byte.
- **Flags mark what would run later on your Mac** - the return path an agent can use even when boxed: git hooks and git configuration (`core.hooksPath`, `core.fsmonitor`, filters), the agents' own configuration and instructions (`.mcp.json`, `.claude/`, `.codex/`, `opencode.json`, `.cursor/`, `CLAUDE.md`, `AGENTS.md`), CI workflows, editor tasks and `.envrc`, build scripts, package manifests, Xcode projects and schemes, new executables (files the agent writes carry no quarantine attribute, so Gatekeeper will not check them), and symlinks that point outside the project. Any other hidden file is marked too. Names are matched without regard to case (`.GIT/hooks/pre-commit`, `claude.md`, `makefile`: the default macOS volume takes them for the same files), and a repository whose folder is not named `.git` (a bare one) has its hooks and configuration flagged like any other (since 0.5.14). Flags are a review aid, not a security boundary. `--fail-on high` exits with status 2 when something high is flagged, for scripts.
- **Undo restores only what changed and loses nothing.** Each changed entry is put back from the snapshot; the agent's version is moved into the session folder, mirroring its path, never deleted; the snapshot stays. The project folder keeps its identity, so editors and shells with it open stay attached. `undo --whole-tree` instead swaps the whole folder with a copy of the snapshot in one atomic step. Stop the agent before undoing either way.
  - `undo --path P` (repeatable) restores only the entries given, as the report lists them (or as absolute paths inside the project), and everything under them; `.` is the project folder's own permissions. The rest stays undoable, and the session counts as undone once nothing changed is left.
  - A path that did not change is refused before anything moves. So is an entry inside a folder the agent deleted or replaced, which cannot come back without that folder (undo the folder). Inside a folder the agent added, a flagged entry the report lists is moved aside on its own; anything else there is refused (undo the added folder).
- **Neither undo nor discard can be blocked by the agent.** Folders it made read-only or unreadable, files it locked (`chflags uchg`) and access control lists it added (`chmod +a "everyone deny delete"`) are opened up first; symlinks are never followed. Sockets and FIFOs are left out of the snapshot.
- **An agent still running cannot steer the undo out of the project** (since 0.5.8). Undo opens the project folder once and reaches every entry from there by name, never through a link, so a folder the agent exchanges for a link to somewhere else while the undo runs is refused (that entry is reported as not restored) instead of followed. Nothing in the project is opened for its content either: a FIFO, socket or anything else found where an entry is to be restored is moved into the session folder like the agent's other versions. Stopping the agent first is still what makes an undo complete.
- **What an agent leaves cannot stop the next snapshot or the cleanup** (since 0.5.14). A file or folder nobody can read (mode 000, an access control list that denies it) is opened up for the moment it is cloned and gets its permissions back, in the project and in the snapshot. A tree nested deeper than a path may be long (1024 bytes) is snapshotted, deleted by `discard` and put back by `undo --whole-tree` like any other. Before, either one left in a project made every later `session start` fail, and a too-deep tree that an undo had moved into the session folder could not be discarded.
- **Guard rails.** A session refuses `/`, your home folder or any folder containing it, and folders overlapping the agent-vm store; only one active session per project.
- **A session's report also says what ran and what was contacted** (since 0.7.17). A program that `agent-vm exec --project`, `box shell --project` or avm starts for a project while a session is active for it is of that session: its line in the box's exec log names the session, and the session's folder notes the box (`runs.jsonl`). `session report` then lists, after the changes, those programs (when, exit status, how long, the command) and the network of their boxes from the session's start to its end, by host, the host most was sent to first. So one command answers what a run changed, ran and contacted. Three things to know:
  - **The network is the box's over that time, not the programs' alone:** the proxy cannot tell which program made a connection, so anything else that ran in the same box meanwhile is counted too. A box made for the run (avm's temporary box, a disposable box) has nothing else.
  - **A box deleted since is read from its kept logs,** which name the sessions whose programs they hold; while one of those sessions is not discarded, `box gc` does not remove the logs for their age. `store logs --remove` removes them by hand, and a store that keeps no logs (`--hold-days 0`) keeps none for a session either: the report then says the box's logs are gone.
  - **With `--json`** the report has `boxes`, `programs` (each with `box` and `program`, the entry of `box execlog --json`), `network` (as `box netlog --summary --json`) and `activityNotes` beside its other keys. avm ends a run with one line of it: "1 program in box avm-dev-1a2b3c; 12 hosts, 4 MB sent, 2 refused".
  - `box execlog <box> --session <id>` lists the session's programs in one box, and `box netlog <box> --session <id>` the box's connections over the session's time (with `--summary`, `--host`, `--kept` as usual).
- **A discarded session keeps its report** (since 0.7.18). The change report was made from the snapshot each time, so once `session discard` (or avm, for a run that changed nothing) removed the snapshot, nothing said what the run had changed. The report is now saved in the session's folder (`report.json`) when the session ends, or at the undo or discard of one that had not ended, and `session report` prints it for a discarded session, marked as saved, with its programs and network as for any other. It is what the run had changed by then, not what differs now (what the project became after the session ended is not in it); nothing can be compared or undone from it (`--json`: `saved` is true and `snapshotPath` is absent). A session undone before it was discarded keeps the report of its end, or of the moment before the undo when it had not ended (as when avm undoes a run). Sessions discarded by an earlier agent-vm have none.
- **Where state lives.** `~/Library/Application Support/agent-vm/Sessions/<id>/`, or `$AGENT_VM_HOME/Sessions/<id>/`. The project must be on the same APFS volume as the store; for a project on another volume, point `AGENT_VM_HOME` at a folder on that volume.
- **A snapshot of the git folders only** (since 0.7.34): `session start --git-only` (avm: `--git-snapshot`) snapshots every entry named `.git` under the project and nothing else, which takes seconds where the whole snapshot of a huge folder takes minutes. The report and undo are then of those folders alone: history, branches, hooks and configuration are covered, working files are not (git can restore tracked ones from the last commit). `undo --whole-tree` is refused for such a session. A repository deleted with its folder gets its `.git` back too: undo makes the missing folders again (since 0.7.35). See [Docs/avm.md](Docs/avm.md#a-snapshot-of-the-git-folders-only), and [Docs/git-snapshots.md](Docs/git-snapshots.md) for what it protects and how to work with it.
- **Known limits.** Access control lists and extended attributes an agent adds or changes are neither reported nor undone. A project file that you hard-linked to a file outside the project is put back in the project by an undo, but what the agent wrote through it stays in the file outside. A report does not look inside a folder nobody can read, or below the depth a path reaches: it lists that folder as changed every time, and undo replaces it as a whole (for a too-deep one, with `undo --whole-tree`). An access control list that denies reading the list itself cannot be saved, so an entry loses it (and a lock flag it hides) when it is snapshotted. An extended attribute of a folder that macOS keeps to itself (such as `com.apple.security.private.scoped-bookmark-key`, on a folder an application was given lasting access to) is not in the snapshot, so a folder that undo puts back whole comes back without it (since 0.7.25; before, such a folder made the snapshot fail). Sockets and FIFOs are neither snapshotted nor reported.
- **For programs.** Every session command accepts `--json`: the session record, the change report, or the undo result. Records and reports carry `snapshotPath`, the snapshot folder to compare files with, until the session is discarded. `discard --older-than DAYS --json` lists the sessions it discarded; active sessions are never discarded by age.

| State | Meaning |
|---|---|
| `active` | Snapshot taken; the agent may still be working. |
| `ended` | The run is over; undo is still available. |
| `undone` | The project was restored; what the agent left is kept in the session folder. |
| `discarded` | Snapshot and replaced tree deleted; only the record remains. |

## Boxes and exec

A box is an instant copy-on-write clone of a ready image with its own identity (MAC address, machine identifier). `box start` runs it in the background under a supervisor process that owns the virtual machine; `agent-vm exec` runs programs in it.

```sh
agent-vm box create dev1 --image dev --allow pack:github --allow pypi.org   # instant APFS clone
agent-vm box start dev1                       # boots in about 10 seconds, waits until ready
agent-vm exec --box dev1 -- uname -a
printf 'b\na\n' | agent-vm exec --box dev1 -- sort
agent-vm exec --box dev1 --cwd /tmp --env FOO=bar -- sh -c 'echo $FOO; pwd'
agent-vm box shell dev1                       # a login shell in the box, on this terminal
agent-vm exec -t --box dev1 -- top            # any full-screen program
agent-vm box view dev1                        # the box's screen in a window (view only)
agent-vm box send dev1 ~/Downloads/Setup.pkg  # copy files or folders into the box's Downloads folder
agent-vm box execlog dev1                     # what exec and shell ran there
agent-vm status                               # every image and box, what runs; quick, measures and deletes nothing
agent-vm status --check-updates               # the same, after asking Apple for the newest macOS: names the images behind it
agent-vm box status dev1                      # its state, supervisor and running programs; starts nothing
agent-vm box list
agent-vm box info dev1                        # its status plus its space on disk
agent-vm box stop dev1                        # clean shutdown through the guest daemon
agent-vm box set dev1 --memory-gb 12 --cpus 6 # a stopped box's size; what it holds stays
agent-vm box rename dev1 work                 # a stopped box's name; what avm remembers follows
agent-vm box recreate dev1                    # a fresh clone of its image, same settings (stopped boxes only); box list says when one is needed
agent-vm box delete dev1
agent-vm box create s1 --image dev --disposable     # a box for one session
agent-vm box start s1 --owner-pid $$               # stops when this shell exits; box gc deletes it
```

- **`exec` behaves like the program itself.**
  - stdin, stdout and stderr are streamed: about 550 MB/s out of the box, 430 MB/s into it.
  - SIGINT, SIGTERM, SIGHUP, SIGQUIT, SIGUSR1 and SIGUSR2 go to the program's process group. When the program does not end, a second SIGINT, SIGTERM, SIGHUP or SIGQUIT between 1 and 30 seconds after the first ends `exec` itself with 128 + the signal number (without a terminal; since 0.6.10): the connection closes, and the box hangs the program up and kills it 3 seconds later.
  - The exit status is the program's: 128 + the signal number when a signal ended it, 127 when the program is not found, 126 when it cannot be started, and 125 when agent-vm itself fails (for example, the box is not running). A closed output (`exec ... | head -1`) ends `exec` with 141, as SIGPIPE would end the program locally, and the program is hung up.
  - If `agent-vm exec` is killed, the program gets SIGHUP, then SIGKILL 3 seconds later.
  - Programs run as the box user in their home folder unless `--user` or `--cwd` say otherwise.
- **API keys and other credentials:**
  - `--env NAME` without a value passes on the value agent-vm was given, as `docker run -e NAME` does: `ANTHROPIC_API_KEY=... agent-vm exec --box dev1 --env ANTHROPIC_API_KEY -- claude`. Unlike docker, a variable that is not set is an error, not a silent omission.
  - `--env NAME=VALUE` puts the value in agent-vm's own argument list, which every user of this Mac can read with `ps` while the command runs. For a key, use `--env NAME` (passed on from the environment), `--env-file` or `--secret`.
  - `--env-file PATH` reads one `NAME=VALUE` per line, the value taken as is to the end of the line (no quotes or escapes); a line with only `NAME` passes that variable on, and `#` starts a comment line. The file may be a pipe, so a password manager can hand keys over without a file on disk: `--env-file <(op read ...)`. Later sources win: the proxy settings of a proxied box, then the files, then `--env`.
  - `--secret NAME` takes the value from your login Keychain instead, stored once with `agent-vm secret set NAME` (the value is read from stdin, typed without echo on a terminal, never from the command line): `agent-vm exec --box dev1 --secret ANTHROPIC_API_KEY -- claude`. `--secret VAR=NAME` names the variable differently. A secret wins over `--env`, and one that is missing or cannot be read ends `exec` with status 125, naming the secret. `box shell` takes `--secret` too.
  - The values go in the exec request straight to the guest daemon. agent-vm does not log them or write them anywhere, and its error messages name variables, never values.
  - What this does not protect: every program in the box can read the value, and an agent can send it to any host the network allows, so an allowed host that accepts uploads is a way out. Prefer keys limited to the task that you can revoke.
- **Looking inside a box:**
  - `box shell <name>` opens the account's login shell in the box on your terminal (`--user root` for root, `--project` to start in a shared project). It is `exec --tty` with the shell, over the box's private channel: SSH stays off and no network is involved.
  - `exec -t` (`--tty`) runs any program on a terminal in the box: editors, `top`, agents with a full-screen interface. Your terminal is put in raw mode, so keys such as Control-C go to the program as typed, and window size changes follow. SIGHUP or SIGTERM to `agent-vm` ends the session, as for ssh. Its output, standard error included, arrives on standard output. The terminal is described as yours: your `TERM`, and the variables that say which terminal it is (`COLORTERM`, `TERM_PROGRAM`, `TERM_PROGRAM_VERSION`, `LC_TERMINAL`, `LC_TERMINAL_VERSION`), so agents draw 24-bit color, links and the enhanced keyboard (Shift+Enter) as they would on your Mac; `--env` overrides any of them. When macOS in the box has no terminal definition for your `TERM` (Ghostty's `xterm-ghostty`, kitty's `xterm-kitty`), your Mac's definition (`infocmp -x`) is installed into the account's `~/.terminfo` in the box first; if that fails, `TERM` is `xterm-256color`. The window's size in pixels goes along too, for programs that draw images (images whose guest daemon has the `terminal-pixels` feature). A program that waited on a prompt during the session is named again when it ends, since a full-screen program may have drawn over the notice. What the program prints goes through a filter first (since 0.6.5): everything that draws in the window passes (text, colors, cursor movement, the alternate screen, mouse and keyboard modes, window titles, links to web pages, and questions whose answers the terminal types back into the session), and what would reach past it is dropped: reading the clipboard, and writing it without `--clipboard` (OSC 52; see below), the answerback question (ENQ, since 0.7.24), the folder new tabs open in (OSC 7), notifications, links to anything but `http` and `https`, iTerm2's file and upload sequences (OSC 1337), kitty's graphics and file transfer, sixel images, tmux's passthrough, moving, resizing or reporting the window, and switches to other encodings or to 8-bit answers. When the session ends, the modes the program left on (mouse reporting, bracketed paste, focus events, the alternate screen, a hidden cursor, line wrapping turned off, kitty keyboard flags, xterm's modifyOtherKeys) are turned off, and input the terminal typed but nobody read is discarded, so an answer to a question the program asked as it ended does not land in your shell.
  - **Copying from a program in a box** (since 0.7.24). An agent with a full-screen interface takes the mouse: a drag in your terminal goes to the agent, which draws the selection itself and copies by asking the terminal to (OSC 52). So the terminal's own Copy has nothing selected, and the request used to be dropped. With `exec --tty --clipboard`, which `avm` passes unless you give it `--no-clipboard`, agent-vm puts the text on your Mac's clipboard itself, in any terminal, while you are using the session: a key or a mouse report of yours went into the box within the last 2 seconds. It does not matter how the program copies (when the button is released, on a key, on a typed command). Answers the terminal types by itself (to a program's questions about the cursor, colors or features) and focus reports do not count as you, nor does input that was typed before the session began or that the box kept waiting before reading it, and at most 4 requests are taken in 2 seconds. The text is plain text, 768 KB at most, with control characters removed (line ends and tabs stay), and with them the characters that hide or reorder what you read: direction controls and marks, zero-width and other invisible characters, tag characters and variation selectors (the emoji one stays). A request to read the clipboard is always dropped. A request refused because nobody was using the session is counted: the session says so when it ends, and `box execlog` shows it beside the writes (`clipboardWrites` and `clipboardRefusals` in `exec.jsonl`); the text itself is never logged. What this does not check is that the text is what you selected: see [the threat model](Docs/threat-model.md). The Command-C of your terminal never reaches a program in the box; it copies what the terminal itself has selected, which is nothing while the agent has the mouse. To select in the terminal, past the agent, hold Fn while dragging in Terminal (or turn off View > Allow Mouse Reporting), Option in iTerm2, Shift in Ghostty, kitty, WezTerm and VS Code. `box shell` and plain `exec --tty` drop every request, as before.
  - `exec --tty --clear-after` (since 0.7.47) clears the window when the program ends: what is on it down to the cursor moves up into the terminal's history (rows under the cursor, empty as a rule, are erased), and what is printed next starts at the top of an empty window. `avm` passes it for an agent or a shell, so what it asks and reports after the session is not lost among what the session left on the window.
  - **A reader that stops reading holds up its own program, not the box** (since 0.7.46). What `exec` prints goes on to your terminal, a pipe or a file, and any of them can stop taking it: a pager, a paused terminal (Control-S), a slow pipe. Until 0.7.46 output that waited for such a reader stopped every connection to the box: a second `exec` got no answer and failed after 20 s with "the guest is unreachable", and other sessions went silent, until the reader read again. Now the program in the box waits instead, as it would on a full pipe, and everything else in the box goes on. It needs a guest daemon with the `flow-control` feature: `image list` names the images whose daemon lacks it, `agent-vm image update <image> --guest` adds it, and `box recreate` gives it to a box made before.
  - `box execlog <name>` lists every program `exec` and `box shell` ran in the box: start time, duration, exit status, account and command (`--json` adds folders, project and process ids). agent-vm's own steps, such as installing a terminal definition for `--tty`, are not listed. The log is kept on your Mac (`Boxes/<name>/exec.jsonl`), out of the box's reach; when the box is deleted it is kept for 30 days. `--since` and `--until` choose the programs by when they started (since 0.7.15, as for `box netlog`), and the file before the current one (`exec.jsonl.1`) is read too. With `box netlog` it shows what happened in a box. It never records the values of the programs' environment, but command lines are recorded as given, so keep keys out of them; one too long for a 64 KB record is recorded by the first 200 characters of each of its first 64 arguments, marked `argvCut` (since 0.5.10). When agent-vm cannot write the log (under a sandbox profile that does not allow the box folder, for example), `exec` warns on stderr that the run is not recorded, and the program runs anyway.
  - **A program's line also names the environment variables it was handed** (since 0.7.19): `envNames` (from `--env`, `--env-file` and `--secret`) and `secretNames` (the secrets among them, as `agent-vm secret list` names them), shown as `{env API_TOKEN, LANG; secrets api_token}`. Names only, never a value: they answer what a run could have sent out. A name that is not a variable's (letters, digits and `_`) is left out, so a value mistyped before the `=` is not recorded as one.
  - `box events <name>` lists what happened to the box that is neither a program nor a connection (since 0.7.19): it started, its guest daemon answered (`ready`), it stopped; a folder was shared or taken back; its network rules or mode changed, with the rules before and after and whether the box ran, so the network log can be read against the rules in force at the time; its screen was shown; its password or other text was typed into the screen (never what was typed); files were sent, by `box send` or the window's Send button, with their names and sizes; it was renamed (`rename`, since 0.7.39). It is `Boxes/<name>/events.jsonl` on your Mac, one JSON object per line (`event`, `time`, `pid` and what the event has), 4 MB and one previous file; `--last`, `--since`, `--until`, `--session`, `--kept` and `--json` are as for the other two logs, and a deleted box's events are kept with them. `supervisor.log` stays for finding out why a box did not start. A box started by an earlier agent-vm has no events until it is started again.
  - `box view <name>` shows the box's screen in a window on your Mac, as a VM app would; closing the window leaves the box running. It is view only unless you add `--interactive`: keys and clicks do not reach the box. In interactive mode the window has a Type Password button (see the account password under Images). The screen shows the box's desktop (Finder, system dialogs, permission prompts that would otherwise wait unseen). Programs run with `exec` run in the account's desktop session (with an image whose guest daemon has the `user-session` feature), so windows and dialogs they open appear on it, but their terminal output does not: `box shell` and `box execlog` are the way to follow those. The box's supervisor opens the window, so a box started over SSH or by a service, with no screen to draw on, cannot show one. The desktop's wallpaper names the box (dark gray, the box's name and its image), so you can tell windows apart; a box sets its own when it starts, and images show their own name until then. A wallpaper someone picks inside a box is kept. It takes an image whose guest daemon has the `wallpaper` feature (`image update-guest`).
  - **Send copies files from your Mac into the box.** The window's Send button (in view-only and interactive windows alike, and in the `image setup` and `image view` windows), or `box send <name> <path>...` on a running box, copies files or folders from your Mac into the box account's Downloads folder, for installers and anything else to set up by hand on the box's screen. Nothing there is replaced: a name in use gets a number ("Setup 2.pkg"). The copy keeps extended attributes, resource forks and bundles (ditto on both sides), and a download's quarantine attribute comes along, so macOS in the box checks it as your Mac would. The item appears in Downloads only once it is complete; the window shows progress, the button stops a send while it runs, and a stopped or failed send leaves nothing behind. Each send from the window is a line in the box's `supervisor.log`. `box send` prints the name each item got, shows progress on a terminal, and stops on Control-C (SIGINT or SIGTERM: exit status 128 + the signal, with nothing of the item under way left in the box unless all of it was sent already, which the message says, and no further items sent); every path is checked before the first is sent. With `--json`, progress goes to stderr as events (step `send`, Docs/progress-events.md) and the result to stdout, also after a stop or a failure: `[{"source": "...", "name": "Setup 2.pkg"}]`, one entry for each item that arrived. It needs no guest daemon update, and no Full Disk Access (macOS in the box asks only to read Downloads, which a send never does). Reading a file in your own Desktop, Documents or Downloads may make macOS on your Mac ask once whether the program that started the box may.
  - **Programs share the login Keychain with apps in the box.** `exec` and `box shell` run a program in the account's desktop session, as a Terminal window in the box would, so a login an agent keeps in the Keychain works whether it was made through `exec`, `box shell` or an app on the box's screen (`box view --interactive`). Root's programs stay outside it. It takes an image whose guest daemon has the `user-session` feature (`image update-guest`); before, the login Keychain refused programs run with `exec` ("User interaction is not allowed").
  - **A program waiting on a hidden permission prompt is reported.** When macOS in the box asks for permission (for the Downloads folder, say, in an image without Full Disk Access), `exec` and `box shell` print what the program waits on and how to answer it (`box view --interactive`) or avoid it (`image setup`), and `box execlog` marks the run as soon as it happens (a `notice` line in `exec.jsonl`, with the program, its process id and what it waits for). A Keychain dialog (a program asking to use an item another program made) is reported and stopped the same way, as "a Keychain item" (`service` `keychain`); the way to avoid it is to log in with the program itself, so the item is its own. When nobody is at a terminal to answer, waiting helps no one: without a terminal on stdin (a program started by another application), `exec` stops the program that waits, only that one, so what started it sees it fail as if access had been refused, and exec goes on. `--prompts wait` lets it wait for an answer instead (the default on a terminal), `--prompts stop` stops it on a terminal too. It works with images whose guest daemon has the `prompt-notices` feature.
  - Terminals need an image whose guest daemon has them: `image list` names what an image lacks, and `image update <image> --guest` adds it.
- **How it connects:** `exec` asks the box's supervisor, over a Unix socket only you can use (`Boxes/<name>/control.sock`), for a connection to the guest daemon. It then talks to the daemon directly, so the supervisor is not in the data path.
- **Box and image names** are letters, digits, `.`, `_` and `-`, starting with a letter or a digit, and keep their case (since 0.7.54; before, lower case only). A name is matched with its case: `box start work` does not start a box named `Work`, and says that it exists. Two names that differ in case only cannot both be used, since the Mac's disk would keep them in one folder. `box rename work Work` and `image rename dev Dev` change only the case.
- **A box name has to leave room for that socket** (since 0.7.53). The socket is on the Mac, for Linux boxes too, and macOS allows a socket's path 103 bytes, so with the store in its usual place a box name can have at most 39 characters less the length of your account name (31 for an account name of 8 letters), and fewer with a deeper `AGENT_VM_HOME`; never more than 63. `box create`, `box rename` and avm refuse a longer name, avm cuts the image's name in its temporary box names to fit, and `box start` and `box recreate` tell a box that has such a name (made before 0.7.53, or in a store that moved) to take a shorter one with `box rename`. `agent-vm version` says the length for the store in use (`maxBoxNameLength` with `--json`).
- **Boxes need the image's volume**: the clone costs nothing until the box writes, and the box's disk grows as the guest works. `box list` shows each box's folder, and `box info <box>` also its space: all of it, and the part no image or other box shares, which is what `box delete` frees (what the box wrote, plus image blocks the image rewrote after the box was made, for example by `image update-guest`). APFS reports that part per file; `box info --json` has it as `diskUsage` (`bytes`, and `unsharedBytes` unless the volume does not report it) next to `path`. Measuring takes about 0.1 s per box, so the lists and `box status` leave it out.
- **The box's clock follows the Mac's.** On the allowlist network a box has no network time, and its clock falls behind, most of all while the Mac sleeps (one was found an hour and a half behind), which breaks certificates and login tokens. The supervisor sets the guest's clock from the Mac's when the box is ready, every 5 minutes, and at once after the Mac wakes (it notices by comparing a clock that stops during sleep with one that does not); `box sync-clock <name>` does it on demand and prints how far off the box was (`clockOffset` in `--json`, seconds behind; negative when ahead). It needs an image whose guest daemon has the `time-sync` feature (`image update-guest`).
- **`box start` is safe to repeat**: on a running box it reports the box, during another start it waits for that one, and on a box that is stopping it waits for the stop, then starts the box again (with its own `--owner-pid`; a disposable box stays stopped). A `box stop` under way still succeeds. It exits 0 when the box is running, 75 when no VM slot is free, and otherwise non-zero with an `Error:` line (1 for failures, 64 for bad arguments). With `--json` it prints the box's status fields as `box status --json` does (`state` is `running`).
- **Disposable boxes, for one session:** `box create --disposable` makes a box that, once it stops for any reason after its VM started, is never started again: its supervisor leaves a `tombstone` file in the box folder, and `box gc` deletes the folder. `box list`, `box start` and `doctor` run `box gc` first (saying on stderr what they deleted), so stopped session boxes do not pile up. A disposable box without a tombstone is deleted once it is more than 10 minutes old and not running (never started, or its supervisor died); a running box is never touched.
- **A deleted box's logs are kept** (since 0.7.14). `box delete`, `box recreate`, `box gc` and avm's temporary box take the box's folder away, and its logs were the only record of what ran in it and what it contacted. They are moved out first, to `Logs/<box>-<time>/` in the store (`<time>` is when the box was deleted, in UTC): `exec.jsonl`, `network-allowed.jsonl`, `network.jsonl`, `supervisor.log` and a Linux box's `console.log`, each with its `.1` file, and `kept.json`, which names the box and its image. Each command says where they went (`box delete --json` as `keptLogs`). A box that logged nothing leaves nothing. `agent-vm store logs` lists them, newest first, with their folder and size (`--json`: `directory`, `holdDays` and `logs`), `store logs --remove <name>` removes one, and `--remove-older-than <days>` those of boxes deleted that long ago (0: all). They are held for 30 days: `box gc` removes older ones, and so do `box list`, `box start` and `doctor`, which run it. Logs that cannot be moved do not keep a box from being deleted: a warning says why.
  - **They are compressed** (since 0.7.16; gzip, as `exec.jsonl.gz` and so on): the logs of a long-lived box can reach 290 MB, most of it refused connections, and a full-size log of refusals came out at a twenty-fifth of its size when measured. Finder and `gunzip` expand them, and `box execlog <name> --kept` and `box netlog <name> --kept` read them as they are. `kept.json` has what they took in the box (`logBytes`).
  - **What they cost is said** (since 0.7.16): `store logs` ends with the number kept and their size, `store logs --json` has `bytes`, and `status` has a line for them when there are any (`--json`: `keptLogs` with `count`, `bytes`, `holdDays` and `directory`).
  - **`store logs --hold-days <days>` changes the 30 days for this store** (since 0.7.16), and `--hold-days 0` turns keeping off: a deleted box then leaves no logs, and the ones kept so far go at the next `box gc`. The setting is `kept-logs.json` in the store.
- **An owner for a box:** `box start <name> --owner-pid N` stops the box, cleanly as `box stop` does, as soon as process N (one of yours) exits, whatever the reason: an application that starts boxes passes its own process id, so a crash or a force quit never leaves virtual machines running, which would keep the two macOS guest slots taken. The supervisor learns of the exit at once from the kernel (kqueue), without polling. `box start` passes on when process N started, so if N exits and its number goes to another process before the supervisor watches it, that process is not taken for the owner and the box stops (since 0.6.7). On a box that already runs the option is ignored, and `box start` names the owner it has; `box status` shows `ownerPid` and `disposable`.
- **Progress for programs:** with `--json`, `box start` and `box stop` report their steps on standard error as JSON lines, as image builds do ([Docs/progress-events.md](Docs/progress-events.md)).
- **`agent-vm status` is the quick overview.** One line per image (its state, macOS, the image it was built from, what it lacks) and per box (its state and image, whether it needs recreating, and while it runs its supervisor's process id, the process that owns it, its project and how many programs run in it), then the jobs that run or wait and those that ended in the last hour (as `job list` shows them; the section is left out when there are none), then how many virtual machines run on this Mac. It measures no disk and, unlike `box list`, deletes nothing. With `--json`: `images`, `boxes` and `jobs`, each entry as `image list --json`, `box list --json` and `job list --json` give it (plus `jobsError` when the jobs could not be listed, so an empty `jobs` is never a failure in disguise), and `runningVMs` (`count`, left out when processes cannot be listed, and `limit`). A program polling `status --json` sees each job end, since a finished job stays in it for an hour.
- **`status --check-updates` says when a macOS update exists.** It asks Apple for the newest macOS this Mac's virtual machines can run (the lookup of `image fetch-ipsw --check`, a few seconds, needs the internet) and keeps the answer in the store (`Cache/newest-macos.json`). From then on plain `status` and `image list`, without a network and without booting anything, name each ready image that is behind it within its major version: "macOS 27.0.1 available" on the image's line, and a last line with the newest macOS, when Apple was asked, and the command that installs it (`agent-vm image update <images> --macos`). With `--json`: `macOSUpdate` (`version`, `build`, `checkedAt`) in the image's entry, in `status`, `image list` and `image info`, and in `status` also `newestMacOS` (the kept answer) and, when the lookup failed, `newestMacOSError`; a failed lookup is a warning, and the summary is printed with the answer kept before. Nothing asks Apple unless `--check-updates` is given, and nothing is installed. An image is not named when its own `image update --macos` asked Apple after the answer was kept and was offered nothing (what `softwareupdate` offers in the guest is what decides), or when the newest macOS is another major version: that is a new image's job.
- **A box keeps what its image had when it was made.** `box create` (and `box recreate`) records the image's `guestVersion` and `guestDigest` in the box, and, as `imageCreatedAt` and `imageRevision`, when the image was built and how often `image update` had changed it. When the image moves on, `box list`, `box status` and `status` say "needs recreate" for each box of that image, and their `--json` entries have `needs`, a list like an image's, with the `reason`: `{"kind": "recreate", "reason": "image-updated", "macOSBuild": "<the image's now>", "system": "<the image's system now, in words>"}` after `image update` (`system` since 0.7.2; `macOSBuild` only for a macOS image), `"image-rebuilt"` when another image was built under the name, and `{"kind": "recreate", "reason": "guest-update", "guestVersion": "<the image's>"}` after `image update-guest`. `box recreate` makes the box again from the image, with its settings, and what the box kept is lost. A box says nothing about what it did not record: the daemon before 0.4.3, the image's build time and revision before 0.5.0.
- **Every image and box says which system it runs** (since 0.7.2). With `--json`, each entry of `image list`, `image info`, `box list`, `box status`, `box info` and `status` has `guest` (`macos` or `linux`) and `system` (the system in words, such as "macOS 27.0 (26A428)"). `macOSVersion`, `macOSBuild` and `passwordStorage` are there for macOS entries only; a program that reads lists should go by `guest`. A record of a Linux guest has format 3 and no macOS keys, so an older agent-vm refuses to read it rather than treat it as a Mac.
- **`box status <name>` only looks.** A stopped box reports `stopped` from its folder; a running one is asked through its supervisor: `starting`, `running` (the guest daemon answers and `exec` works) or `stopping`, the supervisor's process id, agent-vm version and executable, when it started, the shared projects, and how many programs `exec` and `box shell` run in it now (from any client), plus its guest daemon's version and features. `unresponsive` means something holds the box but its supervisor does not answer within 5 seconds (`statusError` says why). With `--json` it prints the same entry as `box list --json`: the record under `box`, `running`, `path`, and the status fields `state`, `pid`, `supervisorVersion`, `supervisorPath`, `startedAt`, `projects` (each shared folder with `path`, `readOnly` and `programs`, the programs started on it that still run; since 0.7.48), `project` and `projectReadOnly` (the first of them), `activeExecs`, `guestVersion`, `guestFeatures` (each only when known; supervisors older than 0.1.6 give no version, path, start or count), and `needs`.
- **The supervisor** is `agent-vm box serve <name>` in its own session, started with the full path of the agent-vm that started it as its first argument, so a process list tells which binary runs each box, logging to `Boxes/<name>/supervisor.log`. It holds the box's lock, so a running box cannot be deleted or started twice. SIGTERM, SIGINT or SIGHUP to it stop the box cleanly, the same as `box stop`. Started in a login session, it is also an application without a Dock icon or menu (so `box view` can open a window): quitting it, as a logout does, stops the box cleanly too. It does not keep the environment of the shell that started it (since 0.6.7): it gets your home, `PATH`, temporary folder and locale, what macOS sets for every process, and `AGENT_VM_*`, so an API key exported in that shell does not stay in a process that runs for days. What a program in the box is given comes from `exec`, each time.
- **What a box says is shown, never obeyed** (since 0.5.10). Text agent-vm did not write reaches your terminal in many places: the guest daemon's version in `box list`, a refusal or a command's output quoted in an error, a permission-prompt notice, the names of files an agent made in the change report, the output of recipe steps, a recipe's or pack's description. Printed as it came, such text could act on the terminal: replace the clipboard, retitle the window, erase the lines above it and write its own. agent-vm replaces every control character and bidirectional override in what it prints for people with `?` (JSON output is left exact; JSON itself escapes the ASCII control characters), and a file name or a guest's answer cannot start a line of its own in a report or in the supervisor's log. A guest daemon's hello must name a version, a build and features that look like ones, and one program's run delivers at most 32 notices a minute, so a guest can neither flood the terminal nor push earlier records out of `box execlog`. One place passes a box's output through untouched: a terminal session (`exec --tty`, `box shell`, `avm`), where the program in the box draws on your terminal as any program would.
- **A box cannot hold its supervisor up** (since 0.5.9). Everything the supervisor asks of the guest for itself (the daemon's hello, the clock, the network setup, mounting a project, the desktop's settings, the shutdown) has a time limit for the whole answer, 20 seconds for a connection, 15 for an answer and 90 for a command, and keeps at most 1 MB of a command's output; a guest that answers a byte at a time, never stops printing, or reports an exit status no process can have gets its connection closed. So `box stop` always ends: when the guest does not shut down, the virtual machine is stopped without it.
- **Linux boxes** (since 0.7.5). A box made from a Linux image (see "Linux images" below) is created, started, stopped, listed and deleted by the same commands, and `exec` and `box shell` work in it as in a macOS box. What differs:
  - **It starts in about 3 seconds and stops in about 1.** `box start` waits for the guest daemon, as for a macOS box; the limit is a minute. A stop asks the daemon to shut the system down, presses the machine's power button after 45 seconds, and pulls the plug 15 seconds later.
  - **It has no screen.** `box view` says so and names `box shell`. Its supervisor is a plain background program, not an application.
  - **It has no account password.** The box user (`agent`, or the image's `--user`) has a locked password, no sudo and no group but its own. `agent-vm exec --box <name> --user root -- ...` is the way to root, from the Mac.
  - **Programs start with** `~/.local/bin` first in `PATH` (where npm, pip, uv and installers put a user's own tools), then `/usr/local/bin:/usr/bin:/bin` and the `sbin` folders, and `LANG=C.UTF-8`.
  - **Its console is kept:** what the system prints while it boots and runs goes to `console.log` in the box's folder (the last boot's is `console.log.1`), at most 2 MB in the two files however much the guest prints. When a Linux box does not come up, the error ends with the console's last lines.
  - **A kernel fault stops the box** (since 0.7.25). A Linux kernel that meets a fault in itself (an "Oops") goes on running by default, with whatever the fault left wrong in its memory, and can write that to the disk; a box was left with a damaged file system that way. A box is now told at every start to stop at its first fault (`kernel.panic_on_oops`; images made from now on have it in `/etc/sysctl.d/90-agent-vm.conf` too), and when the kernel prints that it panicked, the supervisor stops the box at once: `box list` shows it stopped, `box events` and `supervisor.log` say "the guest's kernel panicked", and the reason is at the end of `console.log`. Programs running in the box end with it. Start the box again; its disk is as the file system's journal left it. A program in a box that gets that line onto the console stops its own box and nothing else. The most common cause found so far is the page size of the guest's kernel: [Docs/linux-boxes.md](Docs/linux-boxes.md#the-kernels-page-size) says which images have the kernel that faults, and `agent-vm doctor`, `box start` and `avm` name them (since 0.7.31).
  - **A box that broke says so** (since 0.7.27). When a program's connection ends because the box's kernel panicked, `exec` and `avm` add a second line: that the kernel panicked and the box was stopped, where the reason is, and how to start the box again. A panic while the box boots stops it at once, not after the boot's time limit. When the box's file system reports errors (ext4 then makes it read-only, and no account can be looked up any more), the supervisor's log says so once, and a program refused with "no such account" is told that the box's disk is damaged and that `box recreate` makes the box again. Both are read from fixed lines of the box's console (`console.log`); a program in the box that prints such a line gets its own box described that way and nothing else.
  - **It does not count against the two macOS guests** (next point): several Linux boxes run at once, and beside two macOS boxes.
  - **`avm` takes Linux images and boxes** like the others (since 0.7.9): `avm new deb-tools` is a temporary Linux box with your folder, made, used and deleted in seconds.
  - **`box send` works** (since 0.7.10): each file or folder lands in the box user's `~/Downloads` under a free name, complete or not at all, as in a macOS box. The Mac packs it with `tar`, without what only a Mac has (extended attributes, access control lists, file flags); modes, links, empty folders and files with holes arrive as they are, and an accented name is spelled the way Linux tools spell it. Measured: an unpacked SDK of 30,721 files and 6,714 links in 5 seconds, every file and link identical.
  - **Everything in one place:** [Docs/linux-boxes.md](Docs/linux-boxes.md).
- **macOS runs at most two macOS guests at once**, whichever applications started them (`agent-vm status` and `agent-vm doctor` count them; with `--json`, `status` has `runningVMs` and doctor's "running VMs" check has `count` and `limit`). Linux guests take none of the two places: `runningVMs` and the check also have `linuxBoxes`, how many of `count` are your own running Linux boxes, and `linuxImages`, how many are Linux images that a command is building or updating right now, and a program shows `count - linuxBoxes - linuxImages` of `limit`. Another application's Linux guest cannot be told from a macOS one, so it is counted as if it were one. A command that needs a VM when none is free (`box start`, `image create`, `image update-guest`, `image setup`, `image view`) fails with exit status 75 and a message that starts with "no free VM slot". A refusal before the first VM starts leaves nothing behind: a new image whose VM never ran is removed, so its name stays free, an image being updated stays as it was, and a disposable box can be started again. A build or update boots more than once, and if another application takes the slot between two boots, the image is marked failed, as after any other failure; delete it (or update it again) and retry.
- **Socket paths:** the control socket's full path must stay under 104 bytes, which a very long `AGENT_VM_HOME` can exceed.

## Jobs: long commands in the background

An image build takes minutes to an hour, a box start half a minute. `agent-vm job start` runs such a command detached, in its own session, so closing the terminal (or quitting the application that started it) does not end it, and records what happened in the store, where any terminal or application sees it.

```sh
agent-vm job start -- image create dev --ipsw latest   # prints the job's id at once
agent-vm job start --after 20260929-101500-a1b2c3 -- image setup dev   # runs once that job succeeded
agent-vm job list                                      # what runs, and what ended in the last week
agent-vm job log 20260929-101500-a1b2c3 --follow       # its progress as it comes, then how it ended
agent-vm job cancel 20260929-101500-a1b2c3             # stops it at its next safe point
agent-vm job forget 20260929-101500-a1b2c3             # removes a finished job's record
```

- **What a job runs:** `image create`, `image update`, `image rebuild`, `image update-guest`, `image setup`, `image view`, `image fetch-ipsw`, `box start` and `box stop`, written after `--` as they would follow `agent-vm`. The command is checked when the job starts, so a mistyped one fails at once rather than in the background. It runs with `--json` (added when missing): its progress events go to the job's `log` and its result to the job's `out`. It runs in the folder `job start` was run from, so a relative path (a recipe file) means what it meant there, and on the same store. Like a box's supervisor, it does not get the caller's whole environment (since 0.6.7): your home, `PATH`, temporary folder, locale and `AGENT_VM_*`.
- **Queues:** `job start --after <id>` waits for that job and runs only if it ends with status 0. When it fails, is canceled or is lost, the queued job ends `canceled` without running, its `error` saying which job and why, and every job queued after it follows; so a chain (a base image, its Full Disk Access setup, the images built on it) runs by itself or stops at its first failure. A job after one that already ended without success is refused; after one that is done it runs at once. Queuing is also how a build waits for a VM slot another build (or a `box stop` job) will free, rather than fail with status 75; a box started by a job keeps its slot until it is stopped.
- **States:** `queued` (waiting for the job it was started `--after`), `running`, `done` (exit status 0), `failed` (another status, with agent-vm's error), `canceled` (after `job cancel`; an image build shuts its guest down first and is recorded as canceled), and `lost`: the job's runner was stopped (killed, or the Mac restarted) before it could record the result. A command whose runner is lost may still be running; `status` shows its boxes and images.
- **`job cancel`** on a queued job ends it at once (and the jobs queued after it). On a running one it sends SIGINT to the command, as Control-C would; it returns at once, and the job ends `canceled` when the command has stopped. A `box start` that is canceled leaves the box starting (the supervisor is its own process); stop it with `box stop`.
- **For programs:** `job start --json` prints the job; `job list --json` is an array of jobs with `id`, `command` (agent-vm's arguments), `targets` (`image:<name>`, `box:<name>` or `ipsw`, what the command works on), `after` (the job it waits for), `state`, `status` (the exit status once it ended), `createdAt`, `startedAt`, `endedAt`, `progress` (the last progress event, [Docs/progress-events.md](Docs/progress-events.md)), `notice` (the text of the last notice), `error` (a failed, canceled or lost job's error, possibly several lines, or why a queued job never ran) and `path`. `job log <id> --json` adds every event (`events`) and the lines that are neither events nor the error (`lines`).
- **Where it lives:** `Jobs/<id>/` in the store: `job.json` (what runs), `log`, `out`, `runner.json` and `end.json` (how it ended). The runner is `agent-vm job run <id>` in its own session; it holds the job's `lock` for as long as it lives, which is how every client tells a running job from a lost one without trusting a process id. Finished jobs are removed a week after they ended (by `job list` and `job start`).

## Terminal sessions: avm

`avm` is the short way into a box from a terminal. Run it in a project folder: it lists your boxes (or makes a new one from an image), starts the one you choose when it is stopped, shares the folder into it at the same path, snapshots it, and runs what you choose there: Claude Code, Codex, opencode, or a login shell. Exit it to come back: avm reports what changed in the folder, and you keep the changes or undo them.

```sh
cd ~/src/app
avm                        # choose a box, then what to run in ~/src/app
avm dev1                   # that box
avm dev1 --agent claude    # Claude Code in it (avm agents lists the agents)
avm dev1 --shell           # a login shell
avm new dev-agents         # a new temporary box from the image, deleted when you leave
avm new dev-agents --name app1   # a new box, kept
avm dev1 -- make test      # a command; its exit status is avm's
avm dev1 --no-project      # share no folder (the shell starts in the box user's home)
avm dev1 --read-only       # share the folder read only (nothing to snapshot)
avm dev1 --no-snapshot     # share it read-write without a snapshot (nothing to undo)
avm dev1 --git-snapshot    # snapshot only the git folders: seconds for a huge folder of repositories
avm dev1 --whole-snapshot  # back to the whole folder; avm remembers the last of these three per folder
avm dev1 --no-clipboard    # what the program copies does not reach this Mac's clipboard
avm list                   # the boxes avm offers, and the choice remembered for this folder
avm agents                 # the agents avm can run, and whether their secrets are set
avm dev1 --dry-run         # print the steps instead of taking them
```

```
$ avm
Box dev1
Claude Code
Starting box dev1
Box dev1 is running (14 s)
Sharing ~/src/app (read-write)
Snapshot of ~/src/app taken (session 20260926-101500-7c1e)
Claude Code in box dev1; exit it to come back here
...
Stop box dev1? [y/N] no
Session 20260926-101500-7c1e: 3 added, 5 modified in ~/src/app; review first: 1 high
Kept. Undo later with: agent-vm session undo 20260926-101500-7c1e
Box dev1 keeps running; stop it with: agent-vm box stop dev1
```

Between the question and the last lines, the changes are shown as a list on the whole window, where you mark what to undo (below).

- **The lists** take the whole terminal window, under an AgentVM banner, and give it back when you have chosen (since 0.7.42): first the boxes, running ones first (with the folder each one shares and how many programs run in it), then stopped ones; then what to run. Arrows (or Control-P and Control-N) move, typing filters, Enter chooses, Escape clears the filter and then quits. The box and what ran, chosen for a folder, are remembered (`connect.json` in the store) and preselected next time. The list of boxes also shows what is snapshotted of the folder, with every choice and what it means; Tab changes it. When the box is named (`avm dev1`), the list of what to run shows it instead. A temporary box that is not running is never offered, and an unresponsive one is shown but cannot be chosen.
- **Agents:** Claude Code (`claude`), Codex (`codex`) and opencode (`opencode`), as an image built with [Recipes/agent-clis](Recipes/README.md) installs them. The list of what to run marks an agent the box lacks; each runs through the account's login shell, as the shell does. When none of an agent's secrets is set (for Claude Code, `CLAUDE_CODE_OAUTH_TOKEN` from `claude setup-token` on this Mac, or `ANTHROPIC_API_KEY`), avm offers to set one in the Keychain: typed without echo, it goes to the Keychain only, and the session reads it from there (`exec --secret`). Or go on without and log in inside the box. When the box does not allow the agent's hosts (`pack:anthropic` for Claude Code), avm asks to add them. The agents come from `agents.json` next to `agent-vm`; your own go in `Agents/<id>.json` in the store (see [Docs/avm.md](Docs/avm.md#agents)).
- **Snapshot, report, keep or undo:** a folder shared read-write is snapshotted before the session (a session, as in [Sessions](#sessions-snapshot-report-and-undo)). Afterwards avm lists every change on the whole window (since 0.7.43), the files that run code later on this Mac first and flagged: Space marks the entry under the cursor to undo, `a` marks all and `n` none, and Enter undoes the marked entries and keeps the rest. With nothing marked, Enter keeps everything, and so does Escape; the snapshot stays, so `agent-vm session undo <id>` still works later. With no changes, the snapshot is discarded. A box left running still has the folder, so stop what the agent left running in the background before you undo (or have avm stop the box); avm asks first when other programs (another terminal or application) use the box. Kept snapshots take space as the folder changes: `agent-vm session discard --older-than 7` frees those older than a week.
- **New boxes:** the list ends with `Temporary box from an image...` and `Kept box from an image...`, then a list of your ready images; `avm new <image>` names the image. A temporary box (`avm-<image>-<6 hex digits>`) belongs to that avm: it is stopped and deleted after the session, before the report, and if avm is killed it stops on its own and `box gc` deletes it. A kept box (named in a question, or with `--name`) stays. A new box allows the agent's hosts, plus `--allow`; `--cpus` and `--memory-gb` set its size.
- **Linux boxes** (since 0.7.9) are offered and run like macOS ones: the lists say "Debian 13" where a macOS entry says "macOS 27.0", the agents are the same programs (an image built with `Recipes/linux-node` and `Recipes/agent-clis` has them), and a login shell is `bash`, which reads `~/.profile`.
- **Two VMs at most:** macOS runs at most two macOS virtual machines at once, and a new or stopped macOS box needs one of them (a Linux box needs none). When none is free avm names the running boxes and exits 75 (or, when you chose in the list, shows it again: joining a running box needs no slot).
- **Folders per box:** a Linux box shares up to 8 folders at once (since 0.7.48), so sessions on different projects can use one box; a macOS box shares one at a time. When the folder cannot be shared now (programs in the box use another folder on a macOS box, or a folder around or inside this one, or all 8), the box refuses: avm says so and shows the list again. Sessions in one box are not kept apart from each other: avm says so when the box already shares another folder (see [Several projects in one Linux box](#several-projects-in-one-linux-box)).
- **Your home folder cannot be shared** (nor `~/Library`, a hidden folder in it, or the agent-vm store). Started there, avm offers to connect without a folder; `--project <folder>` shares another one.
- **Stop the box?** After the session in a kept box avm asks whether to stop it (since 0.7.42), with your last answer for the folder as the default, so Enter repeats it. `--stop` and `--no-stop` answer beforehand. A box other programs still run in is left running, and avm says so. A box left running is stopped with `agent-vm box stop <box>`. avm deletes only the temporary box it made in that run.
- **Exit status:** the program's; 1 when avm could not connect (no such box, a box that did not start, a refused folder, an agent not installed in the box, no snapshot and you chose not to go on); 64 for options that do not go together, an unknown agent, or when there is no terminal (from a script, use `agent-vm exec`); 75 when no VM slot is free; 130 when you quit the list.
- **Installing:** the installer package puts `avm` in `~/.local/bin` next to `agent-vm`. It is a symlink to `agent-vm`; `agent-vm connect` is the same command. A build from source makes the link next to the binary (`.build/signed/release/avm`).
- **Completion** of box, image and agent names (after `to` or `new`: `avm to <Tab>`, `avm new <Tab>`): `avm --generate-completion-script zsh > ~/.zfunc/_avm` (with `fpath=(~/.zfunc $fpath)` before `compinit` in `~/.zshrc`), or for bash `avm --generate-completion-script bash > ~/.avm-completion.bash` and `source ~/.avm-completion.bash` in `~/.bashrc`. The same with `agent-vm` completes `agent-vm connect` and every other command.
- `NO_COLOR=1` turns off bold and reverse video; with `TERM=dumb` (or no `TERM`) the list is a numbered menu. Everything else: [Docs/avm.md](Docs/avm.md).

## Secrets in the Keychain

```sh
printf %s "$KEY" | agent-vm secret set ANTHROPIC_API_KEY   # or type it: agent-vm secret set ANTHROPIC_API_KEY
agent-vm secret list                                       # names only, never values
agent-vm exec --box dev1 --secret ANTHROPIC_API_KEY -- claude
agent-vm secret delete ANTHROPIC_API_KEY
```

- **Where they are:** generic passwords in your login Keychain, service `agent-vm`, account `NAME`, visible in Keychain Access. A name is letters, digits and `_`, since it also names the environment variable.
- **Who can read them:** macOS ties each item to the agent-vm that stored it. Another program, or an agent-vm signed differently, makes macOS ask you first ("agent-vm wants to use your confidential information"), and `exec` waits for the answer. A build from `Scripts/build.sh` signed ad hoc is a new identity after every rebuild, so in development expect that question once per secret after each rebuild: answer Always Allow, or store the secret again with the new build. A Developer ID build keeps its identity across updates.
- **`secret list`** shows whether each secret was stored by this very agent-vm, so reads it without a question (`readable` in `--json`). It reads names and attributes only, never a value, so it never asks: macOS offers no way to find out whether a read would ask without asking, so this is what agent-vm can tell (a secret someone chose Always Allow for is still listed as not readable).
- **What this does not protect:** as for `--env`, every program in the box can read the value, and an agent can send it anywhere the network allows.

## Network: allowlist, off or open

Every box has a network mode, chosen at `box create --net` (default `allowlist`) and changed with `box network`:

| Mode | The box's network card | Reaches | Logged |
|---|---|---|---|
| `allowlist` | leads nowhere (a fixed address, no route, no DNS) | only listed hosts, through a proxy on this Mac | every attempt |
| `off` | leads nowhere | nothing | every attempt |
| `open` | NAT through this Mac | the internet and your local network | no |

```sh
agent-vm box create dev1 --image dev --allow pack:github --allow '*.example.com' --allow api.example.org:8443
agent-vm box network dev1 --allow pypi.org --allow files.pythonhosted.org   # takes effect at once
agent-vm box network dev1 --disallow pypi.org                                # open connections to it are closed too
agent-vm box netlog dev1 --denied --last 20                                  # what was refused, and why
agent-vm box netlog dev1 --follow                                            # watch connections as they happen
agent-vm box netlog dev1 --summary --since 2h                                # by host: what was sent where in the last two hours
agent-vm box packs                                                           # the host lists: built-in and your own
agent-vm box network dev1 --net open                                         # while the box is stopped
```

- **How the allowlist works.** Programs in the box see a system proxy at 127.0.0.1:3128 (set in the guest's network settings, and as `HTTP_PROXY`/`HTTPS_PROXY` for programs run by `exec`). The guest daemon relays it over vsock to a proxy in the box's supervisor on this Mac. That proxy serves `CONNECT` (HTTPS and anything else tunneled) and plain `http://` requests. It checks each against the rules by host name and port, resolves the name here on the Mac, and connects only to public addresses: an allowed name that resolves to this Mac or your local network is refused (a DNS rebinding defense). That includes public-looking addresses on the networks of this Mac's own interfaces, such as the global IPv6 addresses of the Mac and its neighbors (for IPv6, the whole /56 around each address, where a home's other subnets usually are). On an IPv6-only network (a phone's hotspot, some carriers and routers), the DNS server answers with IPv6 addresses that stand for IPv4 ones (NAT64, often under a public-looking prefix): such an address is also judged as the IPv4 address it stands for, using the well-known prefix 64:ff9b::/96 and the network's own, found through `ipv4only.arpa` (RFC 7050); an IP address given as the host is used as given, never translated. Names are looked up exactly as written, never with this Mac's search domains appended, and hosts and ports are taken only in their plain spelling (no empty labels, no `+443`). Addresses that stand for another address through a relay (6to4, Teredo) and the documentation ranges count as not public (since 0.6.2). Nothing else leaves the box: it has no route and no DNS, so tools that ignore the proxy fail at once.
- **Rules:**
  - `github.com` allows exactly that host, and `*.github.com` its subdomains, not the host itself.
  - A rule without a port allows HTTPS (`CONNECT` to 443) and plain HTTP (`http://` requests to 80), and `host:port` allows that port for both. There are no tunnels to port 80 without an explicit rule: raw requests through a tunnel could name any other site the allowed server hosts. For plain HTTP, the proxy writes the `Host` header from the URL itself. A plain request is one request (since 0.6.2): its body is passed on up to its `Content-Length` and nothing after it, so a second request with another `Host` cannot ride on the connection; a request with two lengths, or a length and chunks, is refused. A body sent in chunks (`Transfer-Encoding`) is passed on as it comes: the proxy does not look for its end, and what keeps the server from reading a second request there is the `Connection: close` the proxy sends with every request.
  - `pack:<name>` allows a curated list: `apple-updates`, `github`, `npm`, `pypi`, `swiftpm`, `homebrew`, `anthropic`, `anthropic-connectors` and `openai`, and for apt in a Linux box `debian` and `ubuntu`. `box packs` lists them with their hosts; `box packs --json` gives `[{"name": "github", "hosts": [...], "description": "...", "source": "built-in", "path": "..."}, ...]`, with `replacesBuiltIn` on a user pack that replaces a built-in one, and `problem` (no `hosts`) on a pack file that cannot be used.
    - `anthropic` is what Claude Code needs to sign in and work (the API, claude.ai, and platform.claude.com for the sign-in's token exchange). `anthropic-connectors` (mcp-proxy.anthropic.com) gives Claude Code in the box your claude.ai connectors, such as Gmail and Drive, and so the data they reach: allow it only on purpose.
    - `github`, `homebrew`, `swiftpm`, `npm` and `pypi` allow services that host anyone's content (`github.com`, `*.githubusercontent.com`, `ghcr.io`, the registries): a box with one of them can fetch whatever was published there, and the network log shows the host, not which repository or package. See "Send what it can read to the hosts you allowed" in [Docs/threat-model.md](Docs/threat-model.md).
    - The built-in packs are `packs.json` next to `agent-vm` (`Resources/packs.json` in the repository; `Scripts/build.sh` puts it there), so a list can change without a rebuild. A box whose rules name no pack does not need it. Your own packs are files in the store, `Packs/<name>.json`, each `{"description": "...", "hosts": ["example.com", "*.example.org", "example.net:8443"]}`; one named like a built-in pack replaces it. A pack holds host rules only, never `public`. Boxes name packs, so a changed pack applies when a box starts or its rules change (`box network`). A pack file that cannot be used is listed with why, and a box naming it is refused rather than given the built-in pack of that name.
  - `public` allows any public host name, for web fetches and agents whose hosts cannot be listed, and `public:PORT` another port the same way. Connections are still logged (rule `public`, or the named rule that also allows the host, which is checked first), and every resolved address is still checked as above. It never matches an IP address in any notation (an IP address needs its own rule), a name without a dot, or a name under a domain only a local network answers for: `local`, `localhost`, `internal`, `home.arpa`, `lan`, `home`, `corp`, `intranet`, `private`, `localdomain`, `test`, `invalid`, `example` and `onion` (since 0.5.12; the first four before). Such a name needs a rule of its own, and is then still refused unless its address is public.
  - What the address check cannot see, and `public` therefore allows: a name for your router's public address, which reaches whatever the router forwards to machines at home (a NAS, a camera); and networks with public addresses that this Mac reaches only through a VPN (some companies number their internal networks so). Use named rules on such networks.
- **Which tools follow the proxy** (measured): URLSession programs, `softwareupdate`, Python and pip use the system proxy; curl, git, SwiftPM and Node need the environment variables, which `exec` sets. ssh (and git over SSH) goes through it too: every start of a box on the allowlist network (or `off`) writes `/etc/ssh/ssh_config.d/agent-vm.conf` with a `ProxyCommand` through the proxy (an `open` box has it removed), and the host needs a rule for port 22 (`pack:github` includes `github.com:22`). [Docs/tools-and-the-proxy.md](Docs/tools-and-the-proxy.md) lists what works as is, what needs a setting (Node outside `exec`, Python's aiohttp, Java) and what cannot go through a proxy (DNS tools, ping, UDP, databases).
- **In a Linux box** (since 0.7.5) the allowlist and `off` modes give the guest no network card at all: there is nothing but the loopback, no address, no route and no name lookup, and the only way out is the same proxy at 127.0.0.1:3128. Programs run with `exec` and `box shell` get the proxy variables, as in a macOS box. Three files are written at every start of such a box and removed in an `open` one: `/etc/apt/apt.conf.d/90agent-vm-proxy` (apt through the proxy), `/etc/ssh/ssh_config.d/agent-vm.conf` (ssh, as in a macOS box) and `/etc/profile.d/agent-vm-proxy.sh` (the variables, for shells that `exec` did not start). `pack:debian` allows Debian's package servers, for `apt-get` as root: `agent-vm box network <box> --allow pack:debian`. In `open` mode the box has a card on the Mac's NAT, and the start waits up to 15 seconds for its address. [Docs/tools-and-the-proxy.md](Docs/tools-and-the-proxy.md) has what was measured with Linux tools.
- **The log** (one JSON object per line) records the time, method, host and port, the decision and rule, the address connected to, and the bytes each way. `box netlog` shows it.
  - It is two files in `Boxes/<name>/` (since 0.5.12): `network.jsonl` holds refused and failed connections, `network-allowed.jsonl` the allowed ones. A refusal costs a box nothing to cause, so a box that sends refused requests as fast as it can fills only the first file, and cannot push a connection that went through out of the log. `box netlog` reads both and lists the connections in the order their requests arrived (`time`, in whole seconds, and `timeMilliseconds` within it). Logs written before 0.5.12 have everything in `network.jsonl`, and are read as before.
  - An allowed connection is logged when it opens, with `"open": true`; about once a minute while it carries data, with its bytes so far and `"partial": true`; and when it ends, with its bytes and duration. All its lines carry the same `id`. So a long-lived connection, such as an agent's own to its provider, is in the log with its volume while it runs, not only once it has ended. `box netlog` (with `--json` too) shows each connection once: ended with its bytes; still `open`, with the bytes last noted ("so far"); or, when the box stopped before its end was logged, with the bytes last noted, if any (text: "end not logged"; in JSON neither `open` nor a total, and `partial` on the bytes). The bytes sent up include a plain HTTP request's head (its URL and header lines), which a box chooses as freely as a body.
  - When agent-vm itself ends an allowed connection, its last line says why in `reason`: its rule was removed, or the server stayed silent after the box closed its side.
  - `box netlog --last N` reads only the end of the log, however large it is.
  - macOS's own background services (iCloud, software update checks) show up as refused connections unless allowed, about 2-4 a second from an idle guest.
  - At 64 MB each file moves to `<name>.1`, replacing the previous one; `box netlog` reads on into the `.1` files. A box can still wear the allowed files out, with some two hundred thousand connections that each went through to a host it is allowed; those are then what the log shows.
  - `box netlog <name> --follow` (`-f`) prints the last 10 connections (or `--last N`), then each line as the proxy logs it, until the box stops (Control-C ends it sooner); it carries on across the move to `.1`. An allowed connection then comes as it opens, while it runs and as it ends, with the same `id`. With `--json` it prints one JSON object per line instead of an array, and `--denied` applies to it too.
  - **By time and host** (since 0.7.15): `--since` and `--until` take a time (`2026-10-08`, `"2026-10-08 10:11"`, both in this Mac's time zone, or `2026-10-08T10:11:54Z`) or how long ago (`45s`, `10m`, `2h`, `3d`); a connection counts by when it was made, from `--since` up to and not including `--until`. `--host` takes a name, or `*.example.com` for the names under one, and can be repeated. They go with `--last`, `--denied` and `--json`; `--follow` takes `--since` and `--host`.
  - **`box netlog <name> --summary` adds the log up by host and port** (since 0.7.15): connections made, requests refused and failed, bytes sent and received, the first and the last time, and the rules that allowed them. The host the box sent the most to comes first: bytes sent per host is the number that shows data leaving. A connection that is still open, or whose end was not logged, counts with the bytes of its last line. `--json` prints `hosts` (`host`, `port`, `connections`, `refused`, `failed`, `bytesUp`, `bytesDown`, `first`, `last`, `rules`) and the same five sums for the whole.
  - **A deleted box's log is asked the same way** (since 0.7.15): `box netlog <name> --kept` and `box execlog <name> --kept` take a name from `agent-vm store logs` in place of a box's.
- **What a refusal tells the box.** A request for a host that is not allowed is answered 403 with that. A request for an allowed name that does not resolve, or resolves only to addresses the proxy may not use, is answered 502 with one text for both (since 0.5.12): the addresses are named in the log only, so a box under `public` cannot list the names and addresses of your local network by asking for them.
- **Limits against a hostile guest:**
  - at most 256 proxied connections at once (the next get 503, and a line in the log);
  - 30 seconds to send a complete request head of at most 16 KB;
  - once the box has closed its side of a connection, the server may stay silent for 60 seconds, then the connection is ended (since 0.5.12; before, 256 such connections used up the proxy until the box was restarted);
  - log fields cut to 256 characters.
- **Rules can change while a box runs**: the supervisor rereads them at once, and closes every open connection the new rules no longer allow (since 0.5.12; before, a connection opened under a rule kept running after the rule was removed, until the box stopped). A connection another rule still allows goes on. The mode decides the network card, so it changes only while the box is stopped.
- **Boxes created before network policy** keep running on NAT (`open`).

## Projects: your folder in the box, at the same path

```sh
agent-vm exec --box dev1 --project ~/src/myapp -- swift test      # runs in /Users/you/src/myapp in the box
agent-vm exec --box dev1 --project ~/src/myapp --read-only -- grep -r TODO .
agent-vm session start --project ~/src/myapp                      # snapshot first, to review and undo afterwards
```

- **Same path on both sides**: the project appears in the box at its absolute path on your Mac, so paths in build logs, error messages and editor links match. Programs started with `--project` begin in that folder.
- **Live**: the box edits your real folder, and you see changes as they happen. Take a session snapshot first (`agent-vm session start`) to get a change report with risky files flagged, and undo.
- **Projects per box**: a macOS box shares one folder at a time. While a program started with `--project` runs, a different folder or mode is refused; afterwards, `--project` with another folder replaces the previous one. A Linux box shares up to 8 folders at once (since 0.7.48), each the project of its own programs: see [Several projects in one Linux box](#several-projects-in-one-linux-box).
- **The box has your folder only while a program of yours runs on it** (since 0.7.27; before, the share lasted until the box stopped). Five seconds after the last program started with `--project` ends (an `exec`, a `box shell`, an avm session), the supervisor unmounts the folder in the box and stops sharing it, so a box that goes on running cannot change your files with whatever a session left running in it. The next `--project` shares it again, in under a second; a program that starts within the five seconds finds the folder still there. When the box does not let go of the folder, because a program left behind still works in it, the folder is taken away regardless: the Mac stops sharing it whatever the guest answers, `supervisor.log` says that it was still in use, and what was left running there gets errors from then on. `agent-vm box unshare <box> [<folder>]` does the same at once, for the folder named or every folder the box shares, when it was shared without a program (`agent-vm status` marks it "no program of yours runs on it"); it is refused while programs started on a folder it would take run. avm's own step that shares the folder before the agent starts does not count as a program; the agent's session does.
- **The project's parent folder in the box** must be new or hold only folders, because the share is mounted on it and would hide anything there. So `/Users/Shared/<project>` is refused, since the box has `/Users/Shared/.localized`.
- **Owners map across**: files you own appear owned by the box user inside the box, and what the box user creates is owned by you on the Mac.
- **In a Linux box** (since 0.7.6) the folder itself is mounted at its path (not its parent), so it is the project's own path that must be new or hold only folders in the box. What else differs:
  - **Every account in the box sees every file as its own**, root included, and what any of them creates is yours on the Mac. Inside a box the share has no access control between accounts; the box as a whole is the boundary. The box user does not need your user id.
  - **git works at once.** git refuses a repository that belongs to someone else, and for about a second after root looked at a file the share reports it as root's. agent-vm never looks at your project as root, and it tells git in the box that the shared project, and every repository under it, is a safe place (in `/etc/agent-vm/gitconfig`, rewritten at every share). Nothing outside the project is named there.
  - **The mount ignores setuid bits and device files** (`nosuid,nodev`): a file on your Mac cannot become a way to root in the box. `--read-only` is enforced on the Mac and mounted read-only in the box.
  - **As case-insensitive as your Mac's disk**: `Foo` and `foo` are one file, which Linux tools do not expect.
  - **File watchers in the box do not see edits made on the Mac.** The content is current when read; the change events are missing, so a watching build tool needs a nudge (or polling).
  - **Small files are slow, as in a macOS box:** many small files are 6 to 15 times slower than on the box's own disk. Keep `node_modules`, virtual environments and build output inside the box.
- **Not shareable**: `/` and folders directly in it, your home folder or any folder containing it, anything inside `~/Library` or a hidden folder of your home (`~/.ssh`, `~/.aws`, ...), and anything overlapping the agent-vm store. These are checked by folder identity, so other names for the same folders (`/System/Volumes/Data/Users/...`) are refused too; session snapshots follow the same home-folder rule.
- **Keep build output inside the box.** Large files cross the share quickly (1 GB written in 0.7 s), but creating many small files is about 8 times slower than on the box's own disk, and walking a tree about 30 times slower. Put build products on the box's disk: Xcode's DerivedData already lives in the box user's Library, and `swift build --scratch-path ~/build/myapp` does the same for SwiftPM.
- **How it works**: a macOS box has one virtio file system device and a Linux box 8, each filled on the running box and mounted by the guest daemon. It uses Apple's automount tag: with any other tag, macOS treats the share as a network volume and holds every program not run as root on a privacy prompt nobody can see. The project sits inside a small read-only root mounted on its parent folder, so the guest's volume housekeeping (`.fseventsd`, `.Trashes`) never lands in your project.

### Several projects in one Linux box

A Linux box shares up to 8 folders at once (since 0.7.48), so sessions on different projects can run side by side in one box, sparing the memory and processors a box of their own would take. Each folder is shared while programs started on it run and unshared 5 seconds after its last one ends, as above.

**The sessions in one box are not kept apart from each other.** Every program in the box runs as the same account and reaches every folder the box shares at that moment:

- an agent working on one project can read every other shared folder, and change those shared for writing;
- what it changes in another session's folder is reported by that session's report, as if that session had done it, and that session's undo takes it back;
- each session's own report and undo cover its own folder only.

A box of its own keeps a project apart, at the cost of its memory and processors. avm and `exec` say so when the box they start a program in already shares another folder (`box <name> also shares ...`), and `agent-vm status` lists every folder a box shares.

What is refused while programs run on it: the same folder in the other mode, a folder inside or around it (its mount would hide the other, or be made inside your folder on the Mac), and a ninth folder when programs run on all 8. A folder no program runs on is taken away to make room. A macOS box keeps one folder at a time: only Apple's automount tag gives it a local volume, and the box has one device with that tag.

## Images: macOS installed and set up with no clicks

A golden image is the macOS guest boxes will be cloned from. `image fetch-ipsw` downloads the latest restore image this Mac supports into the store's `Cache/ipsw/`. An interrupted download is resumed by the next run, and one whose file changed on Apple's server starts over (the file's ETag is compared). It refuses to start when less than 10 GB would stay free, counting only space that is free now, not purgeable space. The file is put in place only once Virtualization can load it. `--check` shows the image, its size, what is already downloaded and whether it fits, and downloads nothing; `--json` gives the result: `url`, `macOSVersion` and `macOSBuild` (as image records name them), `totalBytes`, `path`, and `state` (`ready`, `partial` or `missing`); with `--check` also `partialBytes`, `freeBytes` (free now) and `fits`, and without it `downloaded` (whether this run downloaded anything). A file already downloaded is checked again on every run. A finished file that Virtualization says is not a restore image is deleted; one it cannot check for another reason is kept. When the server sends no ETag, a partial download is resumed if the URL and length match. `image fetch-ipsw --list` shows the restore images already downloaded, newest first, and which one is the latest usable; it needs no network. With `--json` it gives an array of `name`, `path`, `bytes`, `macOSVersion`, `macOSBuild`, `latest`, and `problem` for a file Virtualization cannot use. `image create --ipsw` takes a path, the file name of a downloaded restore image, or `latest` for the newest usable one; a bare name is looked for in the current directory first (`./latest` names a file called latest). `image create` installs macOS from a restore image (`.ipsw`) and sets it up without a single click, using the guest provisioning added to Virtualization in macOS 27: the first boot creates an administrator account, logs it in automatically and turns on Remote Login. agent-vm then copies its guest daemon in over SSH, checks that it answers over vsock and runs programs as the account, turns Remote Login off again, and shuts the guest down through the daemon.

```sh
Scripts/build.sh                                    # signed agent-vm and agent-vm-guest
agent-vm image fetch-ipsw                           # the latest restore image this Mac supports (about 27 GB; resumes)
agent-vm image fetch-ipsw --list                    # the restore images downloaded, newest first
.build/signed/release/agent-vm image create dev --ipsw latest --recipe my-tools.json
agent-vm image list                                 # quick: records and folders, no disk measuring
agent-vm image info dev                             # one image with its space on disk
agent-vm image setup dev                            # once: Full Disk Access for the guest daemon, in a window
agent-vm image view dev                             # the image's screen in a window, to set something up by hand
agent-vm image rename dev base                      # its name; its boxes and the images built from it follow
agent-vm image delete dev
```

- **Takes about 6 minutes** on a MacBook Air M5 from a local restore image. About 3 minutes go to installing macOS, and about 3 more to the first boot: the SSH check of the new account, the guest daemon, the Command Line Tools and a clean shutdown. The disk is a 64 GB sparse file that holds about 28 GB after setup, plus about 2 GB for the tools.
- **Developer tools**: Xcode's Command Line Tools (clang, Swift, git, make, Python 3) are installed without a dialog. Their Python is 3.9, which Apple's tools need; [Recipes/python](Recipes/README.md) adds a current one beside it. They are about 530 MB from Apple, so the build needs the internet; `--no-command-line-tools` skips them. Spotlight indexing is turned off in images: boxes have no use for it, and indexing a new disk slowed the tools install from about 2 to 26 minutes. Desktop widgets are hidden too (Desktop & Dock > Show Widgets, off): with the widgets macOS puts on a new desktop, about 20 widget programs start at every login and take 256 MB of the box's memory; hidden, about 3 take 70 MB. Turning them back on in System Settings in a box sticks.
- **The guest daemon** (`agent-vm-guest`, a root LaunchDaemon started at boot) is the only way into a finished image: it runs programs for the host over vsock, needs no network, and accepts connections only from the host. Its protocol is described in [Docs/guest-protocol.md](Docs/guest-protocol.md). `image create` installs the `agent-vm-guest` found next to `agent-vm` (or `--guest-daemon <path>`).
- **Options:** `--cpus` (default 4), `--memory-gb` (8), `--disk-gb` (64; at least 40), `--user` (the account name, default `agent`), `--recipe`, `--no-command-line-tools`. Values below what the restore image requires are raised to its minimum.
- **The account's password** is 24 random letters and digits, kept in your login Keychain (since 0.6.0): one item per installed macOS, service `agent-vm.account`, named by a random identifier that the image's record carries (`passwordID`). Images derived from it and its boxes are clones of the same disk, so they carry the same identifier; the item is removed with the last image or box that names it. An agent-vm older than 0.6.0 refuses such an image and its boxes ("written by a newer agent-vm") instead of looking for a file that is not there.
  - What the Keychain adds: the password is no longer plain text for whatever reads small files under `~/Library` (a backup, a sync or search tool, a sandboxed program allowed to read there). It does not hide the password from a reader of the disk images: automatic login keeps it inside each guest, obscured with a publicly known key.
  - Images made before 0.6.0, and the boxes made from them, keep their `Password` file (mode 0600, in folders only you can open) and work as before. `agent-vm store secure-passwords` (since 0.6.1) moves them into the Keychain: a lineage ends up naming one item, a file is removed only after the Keychain gave the same password back, what is in use is skipped and named (run it again later), what fails is named with its error and makes the command exit 1, and `--except <image>` leaves an image and its boxes alone (a name that is no image is refused). `agent-vm doctor` says how many still have a file, and `image info --json` and `box info --json` have `passwordStorage` (`keychain` or `file`). Every image made by an ad hoc build of agent-vm (`Scripts/build.sh` without a signing identity) keeps a `Password` file too, and such a build refuses `store secure-passwords`: the Keychain ties an item to the program that stored it, and an ad hoc build is a new program after every rebuild.
  - Daily use never reads the password (`box start`, `exec`, `box shell`, `avm`). What does: an image's build, `image setup`, `image view`, a macOS update, the first `box view` of a box (to turn its screen lock off) and Type Password. If the item is missing (a store copied to another Mac, or restored without the Keychain), those say so and name the way out, `image rebuild <image> --ipsw latest` (a new install makes a new password) and then `box recreate`; boxes still start and run programs. An agent-vm signed differently than the one that stored the item makes macOS ask before it reads it; a box's window stays usable while that question is open.
  - During the build, agent-vm reaches the guest with the system's `/usr/bin/ssh` using password authentication, until the daemon is in place. It never uses your SSH configuration, keys, agent or `known_hosts` file: the guest's host key goes into the image folder.
  - You never need to type it: the guest's screen does not lock (no screen saver, no display sleep, no screen lock; set in images, and again in a box when its screen is first shown, since part of it is stored per machine), and when macOS in the box asks for it anyway (an administrator prompt, for one), the window's **Type Password** button, or `box view <name> --type-password`, types it into the focused field. It never goes through the pasteboard.
  - What it guards: inside the box, it is what keeps the agent (an administrator account) from root. It never enters the box as a file or as an argument of a command (since 0.5.11; before, the step that turns the screen lock off named it in a command line the agent could list, see below), and projects in `~/Library` are refused. On your Mac it adds nothing: anything running as you can already get root in a box (`exec --user root`) or read its disk. Weak spots: a box that was shown in a window by an agent-vm older than 0.5.11 may have let its agent read the password, which is the same in every box of that image and in images derived from it, so rebuild such an image from a restore file if an agent in it must not have root (`image rebuild <image> --ipsw latest`); it is in plain text in backups of your Library, it is shared by an image, its boxes and images derived from it, and it is also stored obfuscated in the guest (`/etc/kcpassword`, readable by root only), which automatic login needs.
- **Anything else by hand: `image view <image>`** (since 0.6.14). It boots the image with its screen in an interactive window, as `image setup` does, and opens nothing in it: install an application, sign in, change a setting, then close the window. The image shuts down and keeps what was done; boxes made from it afterwards inherit it, and boxes made before keep what they have (nothing marks them as needing to be made again). The window has Send and Type Password. Whether the guest daemon has Full Disk Access is looked at when the window closes and recorded, so a grant given by hand there is not missed. As a job, its steps are `boot`, `window` and `shutdown`.
- **Full Disk Access for the guest daemon, once per image.** Every program `exec` and `box shell` run is started by `agent-vm-guest`, so macOS asks on its behalf before one opens the box account's Desktop, Documents or Downloads, and in a box nobody sees that prompt: the program just waits. Apple's zero-click setup offers no privacy settings, so `agent-vm image setup <image>` boots the image in an interactive window with System Settings open on Full Disk Access and `agent-vm-guest` shown in Finder: drag it into the list, turn it on, press Type Password when asked, and close the window. The window's Send button copies installers and other files into the image's Downloads folder meanwhile (see `box view`). Boxes made from the image afterwards inherit it. `image list` says which images lack it. macOS ties the grant to the daemon's designated code requirement. The default ad hoc signature's requirement is the hash of one build, so `image update-guest` loses the grant (measured; it says so), and the image needs `image setup` again. With a Developer ID (`Scripts/build.sh --identity ...`), the requirement names the identifier and the team, so every build signed that way keeps the grant (measured across `image update-guest`). Images record the daemon's requirement (`guestRequirement`, and in `fullDiskAccess`), `agent-vm version` shows the local daemon's, and `image list` counts a grant as present for a daemon with the same Developer ID requirement. A client can tell without booting whether `update-guest` keeps an image's grant: it does when `version --json`'s `guestDaemon.requirement` equals the image's `fullDiskAccess.guestRequirement` (with `granted` true) and names a signer: it contains `anchor` or `certificate root`, where an ad hoc build's is `cdhash H"..."`.
- **Where it lives:** `~/Library/Application Support/agent-vm/Images/<name>/` (or `$AGENT_VM_HOME/Images/<name>/`): `image.json` (state, macOS version and build, resources, timings, the guest daemon's version, protocol, features and SHA-256), the disk, the auxiliary storage, the hardware model and the machine identifier. `image list` shows each image's folder and measures nothing, so it stays quick however many images there are. `image info <image>` adds its space, and how much of it no box or other image shares (what `image delete` frees; the rest stays in use by the clones). For an image built with `--from`, a third line gives what its disk added over the image it was built from, which does not change as other images and boxes come and go (only a little when the base itself is started again, by `image update-guest` or `image setup`), so the growth of each layer can be traced (`addedOverBase` in `--json`). It compares where the two disks' data lies on the volume (`F_LOG2PHYS_EXT`), about 0.3 s per image. With `--json`, each list record gains `path` and `needs`, and `image info` also `diskUsage` (`bytes`, and `unsharedBytes` unless the volume does not report it) and `addedOverBase`.
- **When an application runs agent-vm: Local Network access.** The first boot of a newly installed image is the only time agent-vm reaches a guest over the network (SSH to the guest's address on the Mac's virtual network, to put the guest daemon in; everything after goes over vsock). macOS counts that as the local network, and for a program started by an application it asks that application's permission (System Settings > Privacy & Security > Local Network). Programs started from Terminal need none. Without it the connection fails as "No route to host" and names no permission. Since 0.6.13 the build says so after 30 seconds of such refusals and keeps trying, and a build that gives up names the last attempt's error: "SSH did not come up within 600.0 seconds: the last attempt to reach 192.168.64.2 port 22 failed with No route to host".
- **A failed or interrupted build** stays in the list with its state (`installing`, `provisioning`) or `failed` and the reason; delete it and create it again. An image in use by another agent-vm process cannot be deleted.
- **A guest that starts again instead of powering off** (since 0.7.44). A macOS 27 guest can fail at the very end of its shutdown, after its disks are put away, and then starts again; a build or an update used to wait two minutes for the power-off and fail with "the guest did not shut down within 120.0 seconds", throwing its work away. Now the build asks the guest which boot it is in, and one that started again is asked to shut down again, up to three times, with a note: "the guest started again instead of powering off ...; asking it to shut down again". A build that still fails says how often the guest started again.
- **Canceling a build.** Control-C (SIGINT) or SIGTERM during `image create` or `image update-guest` stops at the next safe point instead of killing the virtual machine mid-write: a guest command in progress (a recipe step, the Command Line Tools) is stopped, a macOS install is canceled, the guest is shut down through its daemon (a guest still booting is given up to 30 seconds for its daemon to answer; one that cannot answer is stopped), and agent-vm exits with 128 + the signal (130, 143). A new image is kept as `failed` with the reason `canceled`; delete it. An image whose guest daemon was being updated stays `ready` and unchanged when the cancel came before its daemon was replaced, and is marked failed (`canceled`) after; the images named after it are skipped and listed. `image setup` already ends this way when its window is closed or on a signal.
- **Linux images** (since 0.7.4). `image create <name> --linux debian-13` builds an image of Debian 13 from Debian's own cloud image for ARM, with no clicks, no SSH and no password; `--linux debian` means the newest Debian this agent-vm knows. It takes about a minute after the download (0.2 GB). Boxes made from it start in about 3 seconds (see "Linux boxes" under Boxes and exec).
  - **What is downloaded, and what is trusted.** The image comes from `cloud.debian.org` (or the mirror it redirects to) and is kept in the store's `Cache/linux/`. Debian's checksum list (`SHA512SUMS`) is fetched over HTTPS from `cloud.debian.org` itself at every `image create --linux`, and never from another host: a redirect of the list is refused. The image's SHA-512 must be the list's before anything reads the file, and a cached file is checked again each time it is used. Debian publishes no signature beside the list, so HTTPS to `cloud.debian.org` is what the image is trusted by. When the list cannot be fetched, a cached file that still has the digest it was checked with is used, and a notice says so. `--cloud-image <path>` builds from a file of your own (`.tar.xz`, `.raw`, or a qcow2 file such as Ubuntu's `.img`; told apart by their first bytes, not their names), which is trusted because you give it; its SHA-512 goes into the record.
  - **Ubuntu 26.04 is withheld** (since 0.7.41; built since 0.7.11). `image create --linux ubuntu` is refused with the reason: Ubuntu packages no kernel with 16 KiB pages, and on macOS 27 a box on its 4 KiB kernel can lose kernel memory and stop ([Docs/linux-boxes.md](Docs/linux-boxes.md#the-kernels-page-size)). The rest of this item describes an Ubuntu image for when it is offered again. `image create <name> --linux ubuntu-26.04` (or `--linux ubuntu`) builds an image of Ubuntu's own cloud image for ARM the same way, in about two and a half minutes after the download (0.9 GB). What differs from Debian:
    - **The download** comes from `cloud-images.ubuntu.com`, and is checked against Ubuntu's `SHA256SUMS`, fetched over HTTPS from that host and no other. Ubuntu also signs the list; the signature is not checked (macOS has no tool for it), so HTTPS to that host is what the image is trusted by, as for Debian. The record's `base` has `sha256` beside `sha512`.
    - **The file is a qcow2 disk image**, which agent-vm reads itself (macOS has no tool for it) and writes as a raw disk with holes, in about 3 seconds. Every offset the file names is checked against the file's length before it is used, and what the reader does not read is refused by name: a backing file, encryption, an external data file, a compression other than zlib, any feature bit it does not know, a disk declared larger than 64 GB.
    - **More is sealed away.** Beside what a Debian image loses: snapd (a daemon of root's that any user can reach and that updates programs by itself) with what installs LXD through it; the Ubuntu Pro client, the update and news notices, the firmware updater, the crash reporter and the release upgrader, which ask the network or change the system in the background; `needrestart`, which restarts services after every apt run; and daemons for hardware a box does not have (VMware's tools, multipath, iSCSI, udisks2). The checks name these packages and Ubuntu's timers. `add-apt-repository` goes with polkitd.
    - **apt in a box** needs `--allow pack:ubuntu` (`archive.ubuntu.com` and `security.ubuntu.com`, over plain HTTP through the proxy, where apt checks its signed lists).
    - **Everything else is the same:** boxes, `exec`, `avm`, the share, `box send`, recipes (`linux-node`, `linux-python`, `linux-sudo`, `agent-clis`), `image update` and `image rebuild --linux ubuntu-26.04`. [Docs/linux-boxes.md](Docs/linux-boxes.md) has the differences side by side.
  - **How it is set up.** The disk is unpacked from the archive straight into the image (nothing is unpacked into a folder), as a sparse file: a 32 GB disk that takes about 2 GB. On its first boot the system's own first-boot program (cloud-init) does one thing: it installs `agent-vm-guest` from a small second disk, checked against its SHA-256. It creates no account. Everything else agent-vm runs through the daemon, each step in the build log: the box user (no password, no sudo, no group but its own), the system's updates, `git`, `jq`, `unzip` and `zip`, and the compiler and make (`build-essential`, unless `--no-command-line-tools`), then your recipes.
  - **How it is sealed.** The ssh server is removed (purged, not only disabled: systemd would make it listen on a second kind of socket by itself), with `unattended-upgrades` and `polkitd`; the timers that update packages in the background are off, so an image changes only by what you run; cloud-init is switched off; the network settings fit any network card or none; the resolver answers nobody on the network. Then the build checks what it sealed (no ssh server and no unit for one, the removed packages gone and the timers off, no TCP port open to the network, the daemon and nothing else listening on vsock, no account with a usable password) and fails if any of it is not so. That the box user has no sudo rule and no group but its own is checked earlier, before your recipes run (since 0.7.7), so that a recipe can add a rule on purpose.
  - **Root in a Linux image** is `agent-vm exec --user root`, from the Mac. The box user cannot become root by itself: it has no password and no sudo rule. [Recipes/linux-sudo](Recipes/README.md) is a recipe that gives it one, for an image where you accept that every program in a box can be root; the Recipes page says what that widens and how to see what an agent wanted root for.
  - **Tools in a Linux image** (since 0.7.7). `image create <name> --from <linux image> --recipe ...` works as for macOS, with `--input`, `--set` and `--disk-gb` (a Linux disk grows by 1 GB or more, and the build grows the root file system into it). [Recipes/](Recipes/README.md) has `linux-node` (Node 24 from nodejs.org; Debian's own Node 20 cannot use a box's proxy), `linux-python` (venv, pip, pipx, uv) and `linux-sudo`, and `agent-clis` and `acp-agents` serve both systems: `image create deb-tools --from deb --recipe Recipes/linux-node/recipe.json --recipe Recipes/agent-clis/recipe.json` takes about 20 seconds.
  - **A recipe says which system it is for** (since 0.7.7): `"guest": "macos"` (what a recipe without the key is), `"linux"` or `"any"`. `image create` refuses a recipe for the other system before anything is cloned, downloaded or booted, and `recipe check` shows each recipe's guest.
  - **Options:** `--cpus` (default 4), `--memory-gb` (4), `--disk-gb` (32; at least 8), `--page-size` (since 0.7.30: `4k` or `16k` for Debian, default `16k`; see below), `--user` (default `agent`; not a name Debian or Ubuntu has for its own accounts and groups), `--recipe` (a recipe for Linux says `"guest": "linux"` or `"any"`; one that does not is refused, see below), `--no-command-line-tools`, `--guest-daemon <path>` (default: `linux/agent-vm-guest` next to `agent-vm`, which `Scripts/build.sh` builds when it can, see Building; `agent-vm doctor` says whether it is there).
  - **Its record** says `guest` `linux`, `linux` (`distribution`, `version`, `name`, `kernel`, `architecture`, and since 0.7.30 `pageSize`, the size in bytes of the kernel's memory pages), `base` (`release`, `file`, `url`, `sha512`, `sha256` for an Ubuntu image, and `build`, Debian's own name for the build of its image) and `commandLineTools` (`build-essential` and its version). It has no `macOSVersion`, no `passwordID` and no `fullDiskAccess`: a Linux image has no account password and no privacy settings to grant. Its folder holds `Disk.img`, `EFIVariableStore` (the boot firmware's variables), `MachineIdentifier` and `console.log` (what the guest printed on its console at its last boot, at most 2 MB in two files).
  - **`AGENT_VM_LINUX_IMAGE_URL`** replaces the folder the list and the image are fetched from (a mirror of your own): an `https` address, or `http` on this Mac itself.
- **Images from images.** `image create <name> --from <image> --recipe <recipe.json>` clones a ready image and applies the recipe to the clone. The clone gets its own identity, is built on NAT, and costs only what the recipe adds. It takes minutes instead of a macOS install, so tool sets can be layered and rebuilt quickly: in a test, `dev` to `dev-node` (Homebrew and Node) took 2 minutes, then `dev-agents` (Claude Code, Codex, opencode) 1 minute. `image list` shows each image's base and recipe. Example recipes are in [Recipes/](Recipes/README.md), Xcode among them.
- **A copy of an image, with nothing added** (since 0.7.20). `image create <name> --from <image>` with no `--recipe` makes the clone and applies nothing: an image of its own to set up by hand (`image setup`, `image view`: a sign-in, a license, a setting of a program with a window), to give other processors, memory or a larger disk (`--cpus`, `--memory-gb`, `--disk-gb`), or to try something on before an update, with the original left as it is. It is built as any derived image is: it gets its own identity, is started once to check that it runs (so a macOS copy needs one of the two places for macOS guests for about a minute; a Linux copy took 8 seconds), gets this agent-vm's guest daemon when the base's is older, and its record names its base (`derivedFrom`) and the recipes it inherited. The command's last line says that nothing was added, since a `--recipe` left off by mistake no longer stops it. `image rebuild <copy> --from <base>` is refused: it would make a fresh copy and lose what was set up by hand; delete the copy and create it again for that.
- **A bigger disk for a derived image.** `--disk-gb` with `--from` makes the new image's disk larger than its base's, by at least 8 GB (a disk never shrinks). The disk file is sparse, so the extra room costs nothing until the guest uses it. macOS puts its recovery container last on the disk, where it would block the main container from growing, so agent-vm moves it to the new end of the file before the first boot (its bytes and its partition table entry; the file system inside is untouched), and the guest then grows its main container into the gap (`diskutil apfs resizeContainer`). Growing `dev` from 64 to 96 GB took 62 s in all, and the moved recovery container passes `diskutil verifyVolume`. The move writes the recovery container's data anew, about 1.5 GB that the new image no longer shares with its base. Tart's image builder does the same; deleting the recovery container instead, the other way, stops macOS updates.
- **Several recipes in one image.** `--recipe` can be given more than once: `image create dev --ipsw latest --recipe Recipes/homebrew/recipe.json --recipe Recipes/node/recipe.json --recipe Recipes/agent-clis/recipe.json` applies them in that order to one image, so a later one can use what an earlier one installed. `--input` and `--set` go to every recipe that declares the name (two recipes that share a parameter name get the same value); a name none declares is refused before anything is built, and so is the same recipe given twice. `image list` names them (`recipes homebrew, node, agent-clis`). The image keeps each recipe with the files it copies in its `Recipes/<n>-<name>/` folder, and its record lists them as `recipes` (each with `name`, `folder`, `description`, `digest`, `inputs`, `parameters`, and `inheritedFrom` for the ones that ran in the image it was built from); `recipe` stays one entry for the image's own recipes together: a single recipe's as before, or their descriptions joined by "; " with a digest of their digests.
- **Recipes: anything else you want in the image.** `--recipe <recipe.json>` runs your steps while the image is built, after the Command Line Tools and before the image is sealed: shell commands as the box user or as root, files copied from next to the recipe, and checks that must pass. Output appears in the build log as it happens, and the image records the recipe and its digest. A recipe can also ask for files (`--input NAME=PATH`, streamed into the guest while it builds and deleted after, such as an Xcode `.xip`) and for values (`--set NAME=VALUE`, such as which simulator runtimes to install); the image records both. The format is described in [Docs/image-recipes.md](Docs/image-recipes.md). `agent-vm recipe check <recipe.json>...` says what a build would refuse in a recipe, and warns about what is known to fail later, in a second and without a virtual machine (since 0.6.11). To have an AI agent write a recipe, give it one sentence: "Run `agent-vm recipe guide` and follow it to write a recipe that installs ..." (since 0.6.12); the guide it prints is [Recipes/WRITING-RECIPES.md](Recipes/WRITING-RECIPES.md).
- **Updating an image in place.** `image update <image>` brings a ready image up to date: its system (macOS, or a Linux image's packages), the tools its recipes installed, and the guest daemon. `--system`, `--tools` or `--guest` does only that part (they combine); with none of them, all three. `--macos` is the older name of `--system` and stays for macOS images. Several images can be named; they are updated one after another, every name is checked before the first boot, and the first failure stops the rest.
  - **macOS** takes the update Apple offers within the image's major version (27.0 to 27.0.1, not to 28): `softwareupdate` runs in the guest with the account's password on its standard input, the guest restarts by itself, and agent-vm waits for its daemon to answer on the new build. Measured from 27.0 to 27.0.1 on a MacBook Air M5: about 14 minutes (3 to download 3.2 GB, 8 to prepare, 2 to restart and install), with no click and Full Disk Access for the guest daemon kept. A newer Command Line Tools package is installed too, when the image has the tools. When Apple offers nothing, this part takes about 20 seconds.
  - **A Linux image's system** (since 0.7.8) takes the distribution's own updates: `apt-get update`, `dist-upgrade`, then `autoremove --purge` and `clean`, each a step in the log. About 10 seconds when there is little to install; no request to Apple and no 15 GB rewrite.
    - **Whether anything changed** is told by the list of installed packages before and after: with no difference the image is left as it is, and only the time it was looked at is recorded (`systemCheckedAt`).
    - **A package list that cannot be fetched fails the update.** Left to itself `apt-get update` warns and reports success, and the upgrade after it would find nothing and call the image up to date.
    - **A new kernel is checked before it is kept.** When the update installed a kernel newer than the one running, the copy is booted once more, as after a replaced guest daemon; the image gets the new disk only when that boot's daemon answered, and its record then has the new `linux.kernel`.
    - **What was sealed stays sealed.** What the first build checked (no ssh server, no update timers, nothing listening for the network, no account with a usable password) is looked at before and after the update; something that held before and does not after fails the update. What a recipe of yours changed on purpose did not hold before, and is not counted.
    - **A Debian image moves to the kernel with 16 KiB pages** (since 0.7.30) when its record names no page size, which is every image built before: the kernel is replaced first and the copy booted on it, the update fails if it does not come up with 16 KiB pages, and the updates then run on the new kernel (since 0.7.32; before, they ran on the old one and the boot came last). `--page-size 4k` or `16k` with `--system` chooses the size from then on. [Docs/linux-boxes.md](Docs/linux-boxes.md#the-kernels-page-size) says why.
    - **`--macos` is refused for a Linux image**, with the name to use: `--system`.
    - **Free space:** 3 GB.
  - **Tools** are refreshed by the recipes the image keeps (`Recipes/` in its folder, since 0.4.5): each recipe's `update` steps run, in the order the recipes were applied, then its checks, with the parameters the image recorded. `--set name=value` changes a recorded parameter (a pinned version, say) and records the new value. A recipe without `update` steps has nothing to run, but its checks run, after every update step of the others (since 0.5.7): an upgrade that breaks what another recipe installed fails the update, and the image stays as it was. `--set` is only for recipes with update steps. An image built before 0.4.5 keeps no recipes, so only its macOS is updated. See [Docs/image-recipes.md](Docs/image-recipes.md).
  - **A corrected recipe reaches the images built before it** (since 0.7.26). An image runs its own copies of its recipes, so a recipe fixed in a later agent-vm used to reach only new images: when Homebrew moved `python3` to Python 3.15, every tools update of an image with the python recipe failed at that recipe's check, with no way out but a rebuild. Now, at a tools update, a kept recipe that is an older version of one that came with agent-vm is replaced by the installed one: its update steps and checks run in the kept one's place (the log says "Recipe python: this agent-vm has a newer one than dev-tools keeps"), and the image keeps the new recipe when the update succeeds. agent-vm knows its own recipes by content (`Recipes/history.json` lists the digest of every version each ever had), so a recipe you wrote is never replaced this way, also when it has the name of one of ours. `--kept-recipes` runs the recipes as the image keeps them. `--recipe <path>` gives a newer version of any kept recipe, yours included: it must have the kept one's name (its folder's), and replaces it the same way. Inputs are not read again and the build steps do not run: a new recipe's update steps must bring an image built with the old one to where a new build would be.
  - **The guest daemon goes first** (since 0.7.26). When `--guest` is asked for together with the system or the tools (or no flag at all), and the image has another daemon than this agent-vm's, the daemon is updated and put in place as an update of its own before the rest. A tools update that then fails leaves the image with the new daemon; before, it took the daemon's update down with it.
  - **The guest daemon** is replaced with this agent-vm's when the image has another one, last, and the copy is booted once more to check the new daemon before anything is put in place (about 45 seconds when it is the only thing to do: `image update <image> --guest`). As there, a daemon with an ad hoc signature loses Full Disk Access to the replacement, and the update says so; one signed with a Developer ID keeps it.
  - **The image is never half updated.** The update boots a copy-on-write copy of the image's disk and auxiliary storage (a Linux image: its firmware variables) in the image's `Update/` folder. Only when every step and check passed and the guest shut down do the copies take the image's files' place (the folder is renamed `Update.commit`, one atomic step, and the next agent-vm command that uses the image finishes the move if this one was killed in the middle of it). A failed step, a failed check, a cancel (Control-C, SIGTERM) or a killed agent-vm leaves the image exactly as it was, still `ready`; the leftover folder is deleted by the next command that uses the image.
  - **The image stays usable while it is updated.** The update holds the image only while it makes its copy and while it puts the result in place; in between, `box create` and `image create --from` work and get the image as it was (such a box says "needs recreate" once the update is in). `image list` and `status` say "being updated" (`"updating": true` in `--json`). A second `image update`, `image setup` or `image delete` of the same image is refused as in use until it ends.
  - **Only when due.** `--if-older-than <hours>` skips an image, without booting it, when every part asked for was updated, or checked and found current, less than that long ago, and its guest daemon need not be replaced. The record keeps the times apart, as `macOSCheckedAt` (a Linux image: `systemCheckedAt`) and `toolsCheckedAt`: `agent-vm image update tools --tools --if-older-than 24` is a quick refresh of the tools that is cheap to ask for before every session, and says nothing about macOS; a macOS update is minutes of waiting and belongs in a job or a schedule.
  - **How long it will take.** The record keeps how long the last update took that installed no macOS update (`updateSeconds`); the next update's first progress event carries it as `expectedSeconds`, and the text form says "the last update took 85 s". Every recipe, step and check is a progress event with its number and how many there are, so a client can show a real progress bar instead of a spinner.
  - **Before a new box, on request.** `avm new <image> --refresh` (and `agent-vm connect new <image> --refresh`) runs `image update <image> --tools` first and makes the box from the result, with one line that says which recipe, step or check is running, the seconds so far and how long it took last time. Only the tools, never macOS; only when asked: without `--refresh` nothing is updated. If the update fails, the image is as it was and no box is made.
  - **Disk space.** A macOS update rewrites about 15 GB of the disk (measured for a 3.2 GB update), which the image then no longer shares with the boxes and images cloned from it before; they keep the old 15 GB until they are deleted or recreated. `image update` refuses below 20 GB free with `--macos`, 5 GB for the tools alone.
  - **Afterwards** the image's record has the new `macOSVersion` and `macOSBuild`, `revision` (how often an update changed the disk) and `updatedAt`; `image list` shows "updated <time>". Boxes made before say "needs recreate". Images built `--from` this one are not touched: update them too, or build them again.
- **Building an image again.** `image rebuild <image>` builds the image again under its own name, from a fresh start and the recipes it keeps, for what `image update` does not do in place: a new major macOS, a new Xcode, a base image that moved on, or a disk that gathered many updates.
  - **Where it starts.** `--ipsw <file>` installs macOS from a restore image (as `image create --ipsw`) and runs every recipe that ran on the image's disk again, in order, so an image built in layers comes back as one image. `--from <image>` starts from a ready image and runs the recipes that image does not already hold. With neither, the image it was built from is the start; an image that was installed from a restore image needs `--ipsw`.
  - **A Linux image** (since 0.7.8) starts again from its release's cloud image with `--linux <release>` (as `image create --linux`: the newest cloud image is fetched and checked, the system set up and sealed, every recipe run again; `--cloud-image` gives a file of your own), or from a Linux image with `--from`. An image that was made from a cloud image needs `--linux`: `agent-vm image rebuild deb --linux debian-13`. The start is always of the image's own system: `--ipsw` is refused for a Linux image, `--linux` for a macOS one, and so is `--from` an image of the other system.
  - **What it runs with.** Each recipe is taken from the image's `Recipes/` folder and runs with the parameters the image recorded; `--set name=value` changes one. An input is read again from where its file was when the image was built (recorded as `path` since 0.5.6); `--input name=path` names another file, a newer Xcode `.xip` for example, and must be given when the file is gone or its place was not recorded. CPUs, memory, disk size and the account are the old image's; the guest daemon is this agent-vm's.
  - **The old image stays until the new one is ready.** The new image is built beside it as `<image>.rebuild`, with everything `image create` does, and the two change places in one atomic step at the end; then the old one is deleted. Until then the old image is ready and boxes can be made from it (`image list` says "being updated", and a second rebuild, an update or a delete of it is refused as in use). A failure or a cancel leaves the image as it was and `<image>.rebuild` failed beside it, for `image list` to say why; the next rebuild removes it, and so does `image delete <image>.rebuild`. A build that finished but could not take the image's place (the image was in use for two minutes) is kept, and the next `image rebuild <image>` only puts it in place.
  - **Afterwards.** Boxes made from the image before keep what they have and say "needs recreate" (`reason` `image-rebuilt`). An image installed from a restore image needs its Full Disk Access granted again (`image setup`); one built from an image inherits its base's. Images that were built from the old image are clones and do not change.
  - **Limits.** An image built before 0.4.5 keeps only its own recipe, without the files it copies and without what ran on its base: it can be rebuilt with `--from` when its recipe copies no files, and otherwise is created anew with `image create`. The same holds for an image built on such a base: `--ipsw` is refused for it, since what ran on the base is not known. A ready image you named `<image>.rebuild` yourself is never touched: the rebuild is refused.
- **`image update-guest` is not there for Linux images** (it boots the image itself, where `image update <image> --guest` works on a copy), and says so.
- **`image update-guest` is deprecated** and will be removed: `image update <image> --guest` does the same on a copy of the image, and plain `image update` brings in the daemon with everything else. It still works, says so on standard error (a `notice` event with `--json`), and no longer appears in `image --help`. What follows describes it until it goes.
- **Updating the guest daemon.** A newer agent-vm may bring guest features (the terminal for `exec -t` and `box shell` is one), and `image list` names what an image lacks (with `--json`, as `needs`: `{"kind": "guest-update", "missing": [...]}` and `{"kind": "full-disk-access", "reason": "not-granted" | "not-checked"}`, empty when nothing is missing). `agent-vm version` shows the daemon `update-guest` would install, with its version, features and SHA-256; an image whose `guestDigest` differs would get it. `image update-guest <image>` boots the image, replaces its `agent-vm-guest` with the one next to `agent-vm` when they differ, and boots it once more to check the new one: about 45 seconds, or 30 when there is nothing to replace. Several images can be named at once (`image update-guest dev dev-node dev-agents`): they are updated one after another, every name is checked before the first boot, and the first failure stops the rest, since a daemon that does not start marks its image failed and would mark the next one too. Boxes made from the image earlier keep their daemon; `box recreate <box>` makes one again from the updated image. `image create --from` puts the current daemon into every image it builds.
- **Progress for programs.** With `--json`, `image create`, `image update`, `image update-guest`, `image setup` and `image view` report their steps on standard error as one JSON object per line (`{"event": "progress", "step": "install", "fraction": 0.4, ...}`, log lines and notices), and print only the image record on standard output; without it, the text is as shown above. The steps and fields are in [Docs/progress-events.md](Docs/progress-events.md).

## Building

```sh
swift build
swift test
Scripts/build.sh                          # release build, signed ad hoc for this Mac
Scripts/build.sh --identity <Developer ID Application identity or team ID>
.build/signed/release/agent-vm doctor     # can this Mac and this binary run boxes?
.build/signed/release/agent-vm version    # versions, protocols, and the guest daemons next to it
```

`Scripts/build.sh` also builds `linux/agent-vm-guest`, the guest daemon for Linux boxes, when this Mac can (since 0.7.1). It is the same source built for 64-bit ARM Linux as one static program, which Xcode cannot do. It needs two things from swift.org, of the same version as each other: a toolchain and the static Linux SDK.

```sh
Scripts/install-linux-toolchain.sh --check    # what is there and what is missing
Scripts/install-linux-toolchain.sh            # install what is missing, after asking
```

That script installs up to three things, each only when it is missing, all into your home folder and none with administrator rights: `swiftly`, swift.org's installer, which is not part of macOS or Xcode (its package must be signed by the Swift project and notarized by Apple); the toolchain, into `~/Library/Developer/Toolchains` (about 5 GB); and the SDK, with its checksum (about 1 GB). The release and the SDK's checksum are named in the script; `--version` installs another release, with the checksum swift.org lists for it. Neither replaces Xcode's Swift: no shell startup file is changed, `swift` in a shell stays Xcode's, and `build.sh` calls the other one by its path. By hand it is `swiftly install <version>` and `swift sdk install <address> --checksum <checksum>`, with both values from https://www.swift.org/install/macos/.

The script uses `$AGENT_VM_LINUX_SWIFT` when it is set, else the newest release toolchain in `~/Library/Developer/Toolchains` that has a static Linux SDK of its own version, else `~/.swiftly/bin/swift`. Without one it says so and goes on: everything about macOS boxes works, and that build cannot create Linux images (`agent-vm doctor` has a line for it). `--require-linux-guest` makes a missing compiler an error, for a release; `--no-linux-guest` skips the step. The Linux daemon is not signed: it never runs on a Mac. `agent-vm version` shows its SHA-256. It is about 11 MB (since 0.7.45; 54 MB before): on Linux the guest sources import `FoundationEssentials`, the part of Foundation without the Unicode library, whose data alone was 34 MB of the file. A guest source file that imports all of `Foundation` on Linux brings it back, and a fast test fails.

Virtualization refuses every virtual machine from a process without the `com.apple.security.virtualization` entitlement (`Resources/agent-vm.entitlements`). Any developer can use it without Apple's approval, but a plain `swift build` does not sign it in, so `session` commands work from `.build/debug/agent-vm` while anything that starts a virtual machine needs the output of `Scripts/build.sh`. The script builds `agent-vm` and `agent-vm-guest`, signs copies in a staging folder and renames them into `.build/signed/<configuration>/` (so running boxes survive a rebuild: macOS stops a process whose signed file is rewritten under it) with the hardened runtime (ad hoc by default, or with a Developer ID and a secure timestamp; `AGENT_VM_SIGN_IDENTITY` sets the default), verifies the signatures, makes `avm` next to them (a symlink to `agent-vm`) and runs `agent-vm doctor` with the result.

`agent-vm doctor` checks the macOS version, Apple silicon, the binary's entitlement and signature, free space for the store, the store folder itself, account passwords still in files, how many virtual machines already run, and whether the Linux guest daemon is there (macOS runs at most two macOS guests at once, whichever applications started them). It exits 1 when something prevents running boxes; `--json` prints the checks for programs.

The store folder (`~/Library/Application Support/agent-vm`, or `$AGENT_VM_HOME`) must be a folder of your own (since 0.5.15). One that group or others may list is made private (mode 700) by the next command that writes to the store; one that belongs to another user is refused, because they could replace what agent-vm keeps and trusts there. On a volume mounted with ownership ignored (the default for external volumes) no permission keeps other users of the Mac out; `doctor` warns.

## Testing

`swift test` runs the unit tests: `AgentVMKitTests` (the library, and `agent-vm connect` on a pseudo-terminal) and `TerminalUITests` (the list and prompts avm draws, on pseudo-terminals). `Tests/Shell/run.sh` runs out-of-process tests: shell scripts that drive the signed binary from `Scripts/build.sh` the way a user or a program would, and check its output, exit statuses and files.

```sh
Tests/Shell/run.sh fast                   # seconds, no virtual machine, a private store per test
Tests/Shell/run.sh extended               # minutes, real boxes from the image "dev"
Tests/Shell/run.sh all --filter network   # both tiers, only tests whose name contains "network"
```

- **fast** covers the CLI (`avm` and `agent-vm connect` included), sessions (report, undo, refusals), the image and box stores, network rules and recipe checks. Each test gets its own `AGENT_VM_HOME` in a scratch folder, so it never touches your images or boxes.
- **extended** starts real boxes: their life cycle, exec (streams, exit statuses, signals, a killed client), terminals, `box shell`, `avm` and the exec log, `box view` (a window appears briefly), the allowlist network (it needs the internet), project shares, and derived images built from recipes. It uses your store (or `$AGENT_VM_TEST_HOME`) and needs a ready image named `dev` (or `$AGENT_VM_TEST_IMAGE`); without one those tests are skipped. The Linux tests (`linux-images`, `linux-boxes`, `linux-exec`, `linux-network`, `linux-projects`, `linux-recipes`, `linux-updates`) need the Linux guest daemon beside agent-vm; the first builds its own images from Debian's cloud image, and the others want a ready Linux image named in `$AGENT_VM_TEST_LINUX_IMAGE` (`agent-vm image create <name> --linux debian-13`) and are skipped without it. They need no signing identity and no Keychain item. Use an image that keeps its account password in a file (made before 0.6.0, or by an ad hoc build): the tests run an ad hoc build, which macOS asks about, after every rebuild, before it reads a Keychain item the installed agent-vm stored. The avm agent tests also need an image built with Recipes/agent-clis, named by `$AGENT_VM_TEST_AGENT_IMAGE`; without it they are skipped. It creates boxes and images named `shtest-*` and deletes them. A full install from a restore image runs only when `$AGENT_VM_TEST_IPSW` names one. The tier takes about 7 minutes, and macOS runs at most two virtual machines at once, so stop other boxes first.

A test that fails keeps its scratch folder, with the commands it ran and their output, and the last lines are printed. `--keep` keeps every folder, and `--agent-vm <path>` tests another binary.
